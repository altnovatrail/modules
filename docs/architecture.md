## 1. Назначение и границы

**Делает:**
- держит официальные модули первого среза: олимпиадную математику 1–6 из MathTrail, школьную математику 3 класса на рабочей тетради и короткие сочинения на английском для любого возраста (architecture 3.10 spec; R41 spec; product 10 spec). Предметов в них два — математика и письмо (R08 spec);
- держит все модули в одном репозитории, пока формат меняется: на новую версию формата все модули переходят одним pull request (R18 spec; R44 spec; repositories 2.1, 4 spec). Разойтись по репозиторию на модуль они могут, когда формат станет v1;
- держит каждый модуль папкой, которую задаёт формат (R46 spec; [текст формата](../spec/format/README.md), раздел 10; concepts 3 spec):
  - в корне папки — паспорт `manifest.yaml`, граф навыков `skill-graph.yaml`, каталоги `traps.yaml` и `techniques.yaml` и шаги решения `solving-steps.yaml`;
  - задачи и уроки — по файлу на каждую, `tasks/<id>.yaml` и `lessons/<id>.yaml`;
  - медиафайлы — в `media/`, eval-набор — в `eval/`;
  - текст лицензии — обязательный `LICENSE`, уведомления лицензий — `NOTICE`, если они нужны.

  Модуль пишется на YAML 1.2.2 с ограничениями формата, а проверяется схемами JSON Schema 2020-12 той версии формата, которую называет его паспорт, — сейчас 0.3 (R44, R45, R101 spec). Где лежат сами папки и как называются — раздел 3.1 (R03). Виджетов в первом срезе нет (product 10 spec);
- держит в eval-наборе синтетические образцы и образцы, которые для eval сделали взрослые добровольцы и авторы (concepts 3 spec; R02 spec; П-16). Файл образца и eval-набор задаёт протокол eval: образец — сообщение `Sample` пакета `novatrail.eval.v1`, а eval-набор модуля — каждый `.json` под его `eval/` (R93, R95 spec; [текст контрактов](../spec/contracts/README.md), разделы 11 и 13). Раскладка внутри `eval/` — плоская, `eval/<id>.json` (подраздел 2.4; поправка 2026-11-06 к R04);
- проверяет модули в CI (architecture 3.10 spec; repositories 4 spec):
  - CLI `module-kit` — схемами и правилами формата: граф без циклов, ссылки, навыки-опоры, ключи, в том числе решателем шаблона, запасные тексты — проверкой утечки; он же сравнивает новую версию модуля по правилам semver с каждой опубликованной версией ниже неё, снятые тоже, по правилам формата, а версию в другой версии формата — по местам, которые формат держит во всех версиях (architecture 3.7 spec; concepts 3 spec; R89, R101 spec; [текст формата](../spec/format/README.md), разделы 2 и 27) — раздел 3.2. CLI CI берёт бинарником релиза `module-kit` по точному тегу и до первого запуска проверяет его подпись рецептом `spec` `release-verify`, а не ставит через `go install` (R77 spec);
  - стендом `sim`, если изменился граф навыков, — с первого тега `sim`. Первые релизы `modules` выходят раньше стенда, и до его тега гейта графа нет, а первый тег `sim` прогоняет уже опубликованные графы (R76 spec; Т-16);
  - файлы образцов eval-набора — рецептом `spec` `sample-check`, без ключа, на каждом pull request, и с форка тоже: тем же кодом, что проверяет примеры `spec` (architecture 3.10 spec; R93 spec) — раздел 3.4;
  - с этапа 2, когда появятся `tutor` и страница образцов `canvas`, — eval-раннером `tutor` на eval-наборе модуля, отдельным ключом платформы у поставщика ИИ — только для eval, не ключом сервисного аккаунта `api` и не своим ключом автора (R24 spec). Job с этим ключом, как любой job с секретом, делает свою работу только на push в `main` и на pull request из ветки самого репозитория. На pull request с форка он не пропускается, а падает и называет причину, и мерж ждёт, пока сопровождающий не прочтёт правку и не перенесёт её в ветку репозитория (R24 spec, поправка 2026-10-20). Pull request Dependabot тоже идёт из ветки репозитория, но секретов Actions не получает (там же). Где лежит ключ и как eval идёт по pull request Dependabot — открытый вопрос Т-28. Его рекомендация: ключ — в Secret Manager `infra` через Workload Identity Federation, eval по pull request Dependabot — после переноса правки в ветку репозитория, а пока кода `infra` нет, eval идёт из devcontainer, с ключом в переменной окружения, а не в CI;
- на релизе собирает CLI `module-kit` пакеты модулей и индекс модулей внутри общего workflow релиза `.github`, а тот их подписывает (R17 spec; repositories 4 spec):
  - пакет — часть для сервера, часть для устройства и опись (R62 spec; [текст формата](../spec/format/README.md), раздел 25). Часть для сервера — канонический вид модуля: всё содержание, в том числе ключи, решения задач и ловушки, с ярусом каждого навыка и числами каждого экземпляра шаблона. Часть для устройства — `LICENSE`, `NOTICE` и медиафайлы, без ключей и текстов модуля. Опись называет модуль и обе части по дайджестам, а дайджест пакета — дайджест описи. Eval-набор в пакет не входит: образцы eval-раннер берёт из папки модуля в CI `modules`;
  - индекс — файл `module-index.json` в каждом релизе, один на все модули и накопительный (R63 spec; [текст формата](../spec/format/README.md), раздел 26). Он называет каждую опубликованную версию каждого модуля по дайджесту её пакета, с тегом релиза, в файлах которого лежит пакет, с навыками-опорами, которым версия учит, и с отметкой о снятии. Записи из индекса не уходят и, кроме отметки о снятии, не меняются;
  - релиз собирает индекс из индекса прошлого релиза и своих пакетов, после номера и до публикации. У первого релиза прошлого индекса нет. Прошлый индекс скачивает и проверяет рецептом `release-verify` шаг общего `release.yml` на раннере, а рецепт `release-files` `modules` получает уже проверенный файл (поправки 2026-11-01 и 2026-11-02 к R63 spec; Т-35 закрыт);
  - версию снимает следующий релиз: его индекс помечает её запись `withdrawn` с причиной — `wrong_key`, `answer_leak` или `unsuitable_content`. Снятие не отменяется, а снятая версия остаётся только для повтора вердикта (R63 spec). Снятую новейшую версию исправляет версия выше неё по semver. Готовое исправление выходит в том же релизе, что и снятие, а снятие исправления не ждёт (вторая поправка 2026-11-02 к R63 spec);
  - имя файла пакета в релизе выводится из записи индекса — без перебора файлов релиза и без REST API: так пакет находят сборка образа `api`, CI `canvas` и повтор вердикта (там же). Само имя — раздел 3.3 (R03);
- отдаёт пакеты по этапам (architecture 3.10 spec; Т-17):
  - этап 1 — пакеты и индекс в релизах `modules`;
  - этап 2 — при сборке образа `api` дайджесты пакетов берутся из индекса релиза. Pull request закрепляет релиз `modules` и его индекс в конфигурации `api` и служит якорем доверия, а его CI проверяет подпись индекса рецептом `release-verify` (R77 spec). С индексом до `api` доходят и отметки о снятии. Файлы части для устройства раздаёт `api`;
  - старые версии пакетов для повтора вердикта берутся из релизов `modules`.

**Не делает:**
- не держит кода платформы: вид канвы и вид проверки — код платформы, общий для всех модулей, а модуль только выбирает его и задаёт параметры (R02 spec);
- не держит инструкций модели: промпты принадлежат платформе, а свободный текст модуля попадает к модели только отдельным помеченным блоком данных (R02 spec; concepts 3 spec);
- не держит работ учеников — ни детей, ни взрослых: модуль публикуется под открытой лицензией, и отозвать его нельзя. Работы учеников, если их берут в eval, лежат вне репозиториев и только с отдельного согласия (concepts 3 spec; П-10);
- не прячет ключи: ключи открытых модулей публичны, как и сами модули. R05 spec не охраняет тайну, а лишь не пускает ключ в приложение ученика (repositories 4 spec);
- не владеет форматом: схемы, правила, примеры и тест-векторы формата лежат в `spec/format/` (R42, R45 spec), а код, который их исполняет, — проверка, пакет, индекс, открытый вид, виды проверки, — `module-kit` (R17 spec; architecture 3.7 spec);
- не публикует сторонние модули: рекомендация О-9 — на этапах 1–3 публиковать только официальные, а сервис реестра появится на этапе 4 (R17 spec; architecture 3.13 spec).

**Данные и связи:**
- данных учеников и секретов нет, как ни в одном репозитории (RULES.md, Hard rules). Как образцы добровольцев попадают в модуль, решил R04 — раздел 3.4. Согласие на них — открытый вопрос П-16; его рекомендация — письменное согласие и ни имён, ни подписей на образцах. Что лежит в образце со страницы образцов и как на него соглашаются — П-18;
- при сборке ни от чего не зависит, кроме `spec`. CI берёт по точному тегу CLI `module-kit` и `sim`, а с этапа 2 — eval-раннер `tutor` (repositories 2.1 spec, repositories 3 spec). Файл релиза NovaTrail — бинарник CLI, индекс прошлого релиза — входит в CI только после `release-verify` (R77 spec; RULES.md, Hard rules);
- общие проверки CI из `.github` подключены (T21 `spec`): поиск секретов, DCO, CodeQL, Scorecard и проверка документов. Мерж в `main` держат все, кроме Scorecard, вместе с quality gate SonarCloud, а ruleset `main` разрешает только merge-коммит (R30 spec; architecture 3.11 spec);
- пакеты читают `sim` — по типам канонического вида из `spec`, без `module-kit`, с этапа 1, — а с этапа 2 `api`, по дайджесту из своей конфигурации, и eval-раннер `tutor` (architecture 3.9 spec, architecture 3.10 spec). Модель ученика помечает своё состояние релизом `modules` (R80 spec);
- с этапа 2 релиз `modules` по точному тегу берёт и CI `canvas`, проверив подпись рецептом `release-verify` (architecture 3.2 spec; R77 spec; Д54 в таблице 4 RUN.md `spec`). Открытые виды задач для сборки страницы образцов CLI `module-kit` строит из части пакета для сервера, медиафайлы берёт из части для устройства, а отметки о снятии CI читает в индексе новейшего релиза `modules` и из снятой версии страницу не собирает. До первого содержания `modules` задачи замера сборка берёт из релиза `tutor` (R25 spec, поправки 2026-10-21 и 2026-10-28; R63 spec; architecture 3.2 spec);
- образцы добровольцев приходят со страницы образцов `canvas` через pull request, который вносит организатор eval-набора (раздел 3.4); на сервер платформы при этом ничего не уходит (architecture 3.2 spec). К первому замеру страница — без хостинга: её сборка скачивается из релиза `canvas` и открывается на устройстве, а во время работы по сети не ходит: задачи и медиафайлы в неё кладутся при сборке. Образцы детей делаются той же страницей, но без pull request, и в репозиторий не попадают (R25 spec);
- лицензия — Apache-2.0, и у содержания, и у кода, и у образцов добровольцев в eval-наборах (R20 spec). Паспорт модуля называет её идентификатором SPDX `Apache-2.0`, а папка модуля несёт её текст файлом `LICENSE` (concepts 3 spec; R46 spec). Уведомления, которых требуют лицензии содержания, — например MIT у задач standalone, — стоят только в `NOTICE` папки: комментарии файлов модуля в пакет не попадают (поправка 2026-10-28 к R46 spec; R62 spec; раздел 3.5). `LICENSE` и `NOTICE` — UTF-8, строки кончаются LF, и git их концов строк не переводит: пакет несёт их байт в байт ([текст формата](../spec/format/README.md), раздел 10);
- порядок работы задаёт сквозной план `spec` — строки 3.4–3.7 [COORDINATION.md](../spec/COORDINATION.md) (R76 spec). Первое содержание — первая пачка олимпиадной математики для первого приложения, на котором автор локально решает задачи в браузере: 20–30 задач standalone на три полосы, без шаблонов и решателей, уроками, а паспорт называет в аудитории и `adult`. Небольшие наборы школьной математики 3 класса и сочинений `modules` пишет для проверки формата (T38 `spec`). Список пачки — раздел 3.6 (R07). Остальной порт — после первой пачки;
- этап 1, вместе с `module-kit`: формат модуля v0 сразу проверяется на трёх модулях двух предметов (repositories 6 spec; R08, R41 spec).

### 2.2. Образцы добровольцев в eval-наборе

- **Суть:** как образец, который взрослый доброволец сделал на странице образцов `canvas`, попадает в eval-набор модуля: кто открывает pull request, что проверяется до слияния, где отмечено согласие на публикацию. - **Имена** называют предмет и аудиторию, а не язык объяснений: языки среза — О-2. Модуль на другом языке объяснений — другой модуль ([текст формата](../spec/format/README.md), раздел 10), и его имя получит суффикс с тегом BCP 47, например `olympiad-math-en`. ID модуля не меняется никогда: полные ID его навыков и задач хранят модель ученика и прогресс.
- **`LICENSE`** лежит и в корне — лицензия репозитория (Д22 в таблице 4 RUN.md `spec`), — и в папке каждого модуля: этот текст пакет несёт на устройство ученика (поправка 2026-10-28 к R46 spec).
- **`.gitattributes`** — `modules/** -text`: git не переводит концы строк ни у одного файла модулей, ни при коммите, ни при checkout. `LICENSE`, `NOTICE` и медиафайлы пакет несёт байт в байт, и CR LF изменил бы дайджест пакета (Д44 в таблице 4 RUN.md `spec`). `LICENSE` или `NOTICE` с CR и так не пройдёт правило `module.plain-text`.

### 3.2. Проверки CI

| Проверка | Когда | Какие модули |
|---|---|---|
| CLI `module-kit`: схемы и правила формата | каждый pull request и push в `main` | все |
| дерево: в `modules/` только папки модулей, ID каждого — `novatrail/<папка>` | то же | все |
| пакет и сравнение с опубликованным | то же | все |
| стенд `sim` | с первого тега `sim` (R76 spec) | с изменённым графом и новые; все — когда pull request меняет тег `sim`; ни одного — в переходе формата |
| файл образца eval-набора: рецепт `spec` `sample-check` | каждый pull request и push в `main`, без ключа | все, у кого в `eval/` есть образцы (раздел 3.4) |
| eval-раннер `tutor` | pull request, с этапа 2 (R24 spec) | с изменённым `eval/` или пакетом, новые тоже; все — когда pull request меняет тег `tutor` (раздел 3.4) |

- **Все модули на каждом pull request.** CLI `module-kit` проверяет каждую папку `modules/*/` и собирает её пакет. Поэтому новый тег `spec` или `module-kit` перепроверяет все модули без особого правила.
- **CLI закреплён в одном месте** — в стадии `toolchain` `.devcontainer/Dockerfile`: бинарник релиза `module-kit` по точному тегу и сумме sha256 (R34 spec).
  - Этот же бинарник берёт и рецепт `release-files` (раздел 3.3), так что CI проверяет модули той же версией CLI, которой их соберёт релиз.
  - Подпись бинарника проверяет рецепт `release-verify` в CI каждого pull request и push в `main` — job «module-kit signature», рецепт `just module-kit-verify`: `SHA256SUMS` релиза и сверка его строк с суммами `ARG`. Дальше бинарник держит сумма (R77 spec; RULES.md, Hard rules; вторая поправка 2026-11-06 к R03).
  - Это отличие контейнера от контейнера `spec` — R10 (CLAUDE.md, Environment).
  - Форму вызова команд `check`, `build`, `index` и `diff` держит architecture 3.6 module-kit: рецепты `modules` цитируют её и сверяют вызов своими тестами (R102 spec; поправка 2026-11-06 к R03).
- **Сравнение с опубликованным.** CI берёт `module-index.json` новейшего релиза `modules` и проверяет его подпись рецептом `release-verify`. Для каждого модуля:
  1. версия есть в индексе — дайджест пакета, который собрал CI, должен совпасть с дайджестом записи. Иначе содержание правили без подъёма версии, и релиз отказал бы по `module-index.one-package` ([текст формата](../spec/format/README.md), раздел 26);
  2. версии нет в индексе — она должна быть выше каждой опубликованной версии модуля, снятые тоже. CLI `module-kit` сравнивает модуль с пакетом каждой опубликованной версии по правилам сравнения версий формата: какие правила — с каждой версией, а какие — с новейшей, говорит формат (architecture 3.7 spec; [текст формата](../spec/format/README.md), раздел 27; поправка 2026-11-02 к R03). Пакеты CI скачивает по записям (раздел 3.3) и сверяет по цепочке дайджестов от проверенного индекса;
  3. опубликованная версия написана в другой версии формата — пока формат v0, так бывает после каждого его перехода (R44 spec). Её пакет CLI читает по местам, которые формат держит во всех версиях: опись, имена файлов пакета, языки, полосы, навыки и `retired_skills`, ключи задач, уроков, ловушек и приёмов. Правила о навыках, `retired_skills` и ID идут и через переход, а часть версии, пока формат v0, — мажорная ([текст формата](../spec/format/README.md), разделы 2 и 27; R89 spec; поправка 2026-11-06 к R03);
  4. индекса ещё нет, до первого релиза, — все версии новые, и сравнивать не с чем.

  Как CI это делает (R11): новейший релиз — наибольший тег `vX.Y.Z` из `git ls-remote`, без токена, у которого `module-index.json` есть; тег, чей индекс отвечает 404, — релиз, который не вышел, и его лог называет. Его `module-index.json` проверяет `release-verify`, а архив каждой версии модулей из `modules/`, снятые тоже, приходит по адресу из записи (раздел 3.3). Из архива берутся только `inventory.json`, `server.json` и `device.json`; архив со ссылкой, особым файлом или путём вне папки отвергается целиком. Дальше — `module-kit diff --index … --published … <пакет>` над пакетом, который собрал `build`, а без релиза — `--first`: что релиза нет, рецепт говорит явно, файлом `first`, и молча пропущенный индекс не проходит. Цепочку дайджестов от индекса к файлам пакета сверяет `diff`, а его код завершения — код job.
- **Изменился ли граф** — для гейта `sim`. Граф изменился, если канонический текст члена `skill_graph` части для сервера отличается от того же члена у новейшей опубликованной версии модуля той же версии формата. У нового модуля граф изменился. Правка комментария в `skill-graph.yaml` графа не меняет. Стенд идёт на пакете, который собрал CI: `sim` читает `server.json` по типам канонического вида, без `module-kit` (architecture 3.9 spec).
- **Переход формата идёт без `sim`.** Если новейшая опубликованная версия модуля написана в другой версии формата, стенд в этом pull request не гоняется. Пакета новой версии `sim` на прежнем теге не прочтёт, а граф в переходе не меняют: его меняют отдельным pull request, когда `sim` перейдёт на новый тег (repositories 4 spec). Что граф не изменился, держит ревью.
- **Гейт — граф,** как велят карточка 3.10 spec, repositories 4 spec и Т-16. `sim` и `engine` читают из канонического вида и задачи (Д44 в таблице 4 RUN.md `spec`), но правка привязок задач гейта не включает. Включать ли, решает T03 `sim`, а до её ответа гейт — граф: так `spec` ответил на строку В5 (Т-16; architecture 3.9 spec; R09). Правка CI под гейт — Д5 в таблице 4 [RUN.md](../RUN.md).
- **Job и рецепты** (R10). Свои job `ci.yml` собирают стадию `toolchain` и запускают в ней рецепты `justfile` скриптом `spec/tools/toolchain/toolchain.sh` из подмодуля. «module-kit signature» — `just module-kit-verify`; «Modules» ждёт его и запускает `just test`, затем `just modules-check`: дерево `modules/`, версия CLI на `PATH` против `MODULE_KIT_VERSION`, `check` и `build` каждой папки во временную папку и ID из `inventory.json` пакета. Затем каждый пакет сравнивает `module-kit diff` — с опубликованными версиями по индексу новейшего релиза или, до первого релиза, с `--first` (R11). Без `modules/` рецепт печатает `modules/: no modules yet` и выходит с кодом 0. Без модулей рецепт в сеть не ходит. Отказ одного модуля не останавливает проверку остальных; код рецепта — наибольший из кодов того, что упало: 1 — дерево, R03 и отказ по правилам, 2 — `module-kit` не смог сделать своё или опубликованные версии не прочесть.
- **Без фильтра `paths` у workflow.** Что гонять, решает сам job. Проверки workflow, пропущенного фильтром, висят «Pending», и обязательная держит мерж (раздел 4).

### 3.3. Релиз

- **Кто и когда.** Свой `release.yml` по шаблону architecture 3.3 .github вызывает общий `release.yml` `.github` после зелёного CI на `main`, если с прошлого релиза изменилось что-то из `paths`. Номер — следующий `vX.Y.Z` своей линии, как у любого репозитория NovaTrail (R31 spec). Вход `previous-file: module-index.json` стоит с первого релиза, а общий `release.yml` для него — не ниже v0.1.14 (раздел 4). Неизменяемые релизы и ruleset тегов `v*` — условие проверки подписи — стоят с 2026-11-06: ruleset `v-tags`, 26725460, с правилами `update`, `deletion` и `non_fast_forward`, без обхода (R77 spec; Д3 в таблице 4 [RUN.md](../RUN.md)).
- **`paths`** — то, из чего собран выпуск (поправка 2026-10-22 к R31 spec). Перечень вида `modules` держит шаблон architecture 3.3 .github, а этот раздел ссылается на него (поправка 2026-11-01 к R31 spec; поправка 2026-11-06 к R03). На `main` `.github` (af40f94, 2026-11-06) шаблон его ещё не несёт, и `.github` внесёт его своим переходом на тег (Д80 в таблице 4 RUN.md `spec`). До тех пор здесь — перечень, который шаблон получит, а где он с шаблоном разойдётся, прав шаблон:

  ```
  :(glob)modules/**
  :(exclude,glob)modules/*/eval/**
  withdrawals.yaml
  justfile
  LICENSE
  .github/workflows/release.yml
  ```

  - R03 даёт правило, по которому перечень составлен, и пробу, а причину, почему в нём нет Dockerfile, несёт и шаблон.
  - Релиз не дают eval-наборы, документы, CI, кроме `release.yml`, подмодуль `spec` и `.devcontainer/Dockerfile`. Пакет и индекс зависят только от файлов модуля и версии формата его паспорта ([текст формата](../spec/format/README.md), раздел 25), а не от версии CLI в Dockerfile.
  - Цена — `justfile` целиком: правка рецепта CI в нём даст релиз с тем же индексом.
  - Магия `glob` — чтобы `*` не совпадала с `/`: без неё `modules/*/eval/*` исключил бы и `media/eval/` модуля.
- **Рецепт `release-files VERSION PREVIOUS`** идёт в контейнере стадии `toolchain`, на дереве коммита без git, подмодулей, сети и токенов.
  - CLI `module-kit` — тот же бинарник из этой стадии, что у CI (раздел 3.2).
  - `PREVIOUS` — путь только для чтения к `module-index.json` новейшего релиза, который общий релиз скачал и проверил `release-verify` до сборки. У первого релиза это пустая строка, и рецепт говорит сборке явно, что прошлого индекса нет (поправка 2026-11-02 к R63 spec).

  Рецепт собирает пакеты всех модулей и индекс: из прошлого индекса, своих пакетов, тега `VERSION` и `withdrawals.yaml` ([текст формата](../spec/format/README.md), раздел 26). Пакет версии, которую прошлый индекс уже называет, своей записи не меняет. Если дайджест такого пакета другой, сборка отказывает по `module-index.one-package`.
- **Файлы релиза** — то, что рецепт кладёт в `dist/`. Имена — из букв, цифр и `. _ + -`, без папок. Bundle `<файл>.sigstore.json` к каждому ставит общий релиз:

  | Файл | Что это |
  |---|---|
  | `module-index.json` | индекс модулей: каждая опубликованная версия каждого модуля, от первого релиза |
  | `LICENSE` | текст Apache-2.0 из корня |
  | `sha256-<hex>.tar.gz` | архив пакета — на каждую версию, которую публикует этот релиз, и только на неё |

  Пакет версии, которую индекс уже называл, лежит в релизе, который называет её запись, и второй раз не выходит. Релиз, который только снимает версии, несёт индекс и `LICENSE`.
- **Архив пакета** назван дайджестом пакета — `package_digest` записи, где `:` заменено на `-`, — с `.tar.gz`. Внутри — пакет файлами, в корне архива, без верхней папки ([текст формата](../spec/format/README.md), раздел 25). Кроме этих файлов и их папок, в архиве ничего нет — ни ссылок, ни других записей:

  ```
  inventory.json  server.json  device.json
  device/LICENSE  device/NOTICE  device/media/<путь>
  ```

  Адрес выводится из записи индекса, без перебора файлов релиза и без REST API: `https://github.com/altnovatrail/modules/releases/download/<release>/sha256-<hex>.tar.gz`. Байты архива ничто не держит, и держать не нужно. Читатель сверяет опись с дайджестом пакета, части — с описью, файлы — со списком части для устройства, и берёт только пути, которые этот список называет.
- **Снятия** — `withdrawals.yaml`, YAML по разделу 4 формата. Форма — `$defs/withdrawals` схемы индекса, `module-index.schema.json`: ID модуля → версия → причина снятия ([текст формата](../spec/format/README.md), раздел 26; поправка 2026-11-06 к R03). Читает файл команда CLI «построить индекс» (architecture 3.7 spec). Например:

  ```yaml
  novatrail/olympiad-math:
    "1.2.0": wrong_key
  ```

  - Форма требует хотя бы одной записи, поэтому файла нет, пока ничего не снято. Тогда рецепт говорит сборке, что снятий нет.
  - Файл входит в `paths`, так что pull request только со снятием даёт релиз (Д45 в таблице 4 RUN.md `spec`).
  - Записи из файла не уходят: повтор снятия с той же причиной ничего не меняет, а другая причина нарушила бы `module-index.entries-kept`. Снять можно и версию, которая выходит в том же релизе (R63 spec).
  - Если снята новейшая версия модуля, её исправляет версия выше неё по semver, а какую часть поднять, решают правила semver. Правка ключа опубликованной задачи — мажорная (concepts 3 spec), так что исправление версии, снятой по `wrong_key`, — следующая мажорная. Готовое исправление идёт тем же pull request, что и снятие, и выходит в том же релизе: иначе до него текущей станет версия ниже снятой, а если снята новая мажорная — прошлая мажорная, и свидетельства снятой о её навыках перенести нечем. Снятие исправления не ждёт (вторая поправка 2026-11-02 к R63 spec; поправка 2026-11-02 к R03).
  - Версию старее новейшей исправить нельзя: в папке модуля живёт одна линия версий, и новая версия выше всех опубликованных (раздел 3.2).
- **Кто берёт релиз.**
  - CI `canvas` — с этапа 2, по точному тегу `vX.Y.Z` релиза `modules`: номер самого репозитория, а не версия модуля. По тегу он читает индекс, а пакеты берёт из релизов, которые называют его записи. Индекс новейшего релиза он читает только ради отметок о снятии (поправка 2026-10-28 к R25 spec).
  - `api` — с этапа 2: pull request закрепляет релиз и его индекс (раздел 1), а сборка образа берёт пакеты по записям.
  - `sim`, который читает пакеты из релизов `modules` (architecture 3.9 spec), находит их по той же раскладке: адрес пакета выводится из записи индекса.
- **Старые релизы** не удаляются и не переписываются: релизы неизменяемы, а по старым пакетам повторяется вердикт (architecture 3.10 spec). Второму релизу нужен индекс первого — его отдаёт общий релиз, с v0.1.14 (строка 3.7 [COORDINATION.md](../spec/COORDINATION.md)).

**Как решали** — подраздел 2.1 до итога детализации, дословно (R08). «Что известно» записано до решения, так что «решает `modules`» там говорит о дне записи, а ответ — в разделах 3.1–3.3.

- **Что известно:**
  - все модули — в одном репозитории, пока формат меняется; разделить их можно, когда формат станет v1 (R18 spec; Т-2; repositories 2.1 spec);
  - что внутри папки модуля и как называются её файлы, задаёт таблица раскладки ([текст формата](../spec/format/README.md), раздел 10; R46 spec). Где лежит сама папка и как она называется, формат не говорит: это решает `modules`;
  - ID модуля — `<издатель>/<имя>`, оба в kebab-case с буквы: `novatrail/olympiad-math` (R46 spec; concepts 3 spec). Официальные модули издаёт проект. Имён школьной математики и сочинений формат не даёт: их называют сами модули;
  - версия модуля — semver `X.Y.Z` в паспорте (R46 spec). Тег релиза `modules` — номер `vX.Y.Z` самого репозитория, как у любого репозитория NovaTrail (R31 spec), а не версия модуля: индекс называет у каждой версии модуля тег релиза, в файлах которого лежит её пакет (R63 spec);
  - релиз другого репозитория дают только файлы, из которых собран его выпуск: шаблон `paths` его `release.yml` — их перечень по виду репозитория, а держит шаблон architecture 3.3 `.github` (поправки 2026-10-22 и 2026-11-01 к R31 spec);
  - индекс один и накопительный, а пакет, чья версия уже есть в индексе, своей записи не меняет. Поэтому релиз может собирать все модули или только изменённые — это решает `modules` (R63 spec). Как пакеты лежат в файлах релиза, тоже решает `modules` (R62, R63 spec);
  - снятия — входом сборки индекса. Файл со снятиями должен входить в `paths` релиза, иначе pull request только со снятием релиза не даст (Д45 в таблице 4 RUN.md `spec`);
  - первый релиз собирает первый индекс. Второму нужен индекс прошлого: его скачивает и проверяет общий релиз, а как файл доходит до рецепта `release-files`, решает T41 `.github` (поправка 2026-11-02 к R63 spec; строка 3.7 [COORDINATION.md](../spec/COORDINATION.md));
  - `LICENSE` и `NOTICE` модуля git не должен переводить в CR LF: иначе изменится дайджест пакета (Д44 в таблице 4 RUN.md `spec`; [текст формата](../spec/format/README.md), раздел 10);
  - `sim` гоняется, если изменился граф навыков, — с первого тега `sim` (R76 spec; Т-16). На новую версию формата модули переходят одним pull request: `sim` гоняется в нём, только если изменился граф, а граф меняют отдельным pull request, когда `sim` перешёл на новый тег (repositories 4 spec);
  - релиз `modules` по точному тегу берёт и CI `canvas`, для страницы образцов, а отметки о снятии читает в индексе новейшего релиза (раздел 1; R25, R63 spec);
  - в MathTrail содержание математики лежит в standalone, в `content/` и `site/` (repositories 7 spec).
- **Варианты** (T01; первый в каждом пункте выбран, раздел 4 — источники):
  - где лежат папки модулей: `modules/<имя>/`, где `<имя>` — вторая половина ID; `<имя>/` в корне, рядом с `docs/` и `spec/`; `modules/novatrail/<имя>/`, путь по полному ID. Векторы индекса формата раскладывают модули релиза как `modules/<name>/` ([текст формата](../spec/format/README.md), раздел 9). Standalone опыта не даёт: его задачи лежат по темам — файл `content/examples/<тема>.json` на тему, со всеми её задачами, — а формат требует файла на задачу (R46 spec);
  - имена: `olympiad-math`, `grade-3-math` и `english-essays`; `olympiad-math`, `school-math-3` и `short-essays`; `olympiad-math`, `school-math-grade-3` и `essays-in-english`; имена с языком объяснений, хотя языки среза — О-2, он открыт;
  - как пакеты лежат в файлах релиза: архив `sha256-<hex>.tar.gz` на пакет, только версии, которые релиз публикует сам; архив, названный по ID и версии, `novatrail+olympiad-math+1.2.0.tar.gz`; архив по дайджесту, но пакеты всех текущих версий в каждом релизе; пакет россыпью файлов; один архив на все пакеты релиза. Файлы релиза GitHub — плоский список, не больше 1000, с безопасными именами. Просьба `api` — имя файла пакета выводится из записи индекса, лучше всего из дайджеста (В6 в таблице 3 RUN.md `api`);
  - собирает ли релиз все модули или только изменённые: все, а в файлах — только новые версии; только изменённые. Рецепт `release-files` получает дерево коммита без git (architecture 3.1 .github);
  - с чем CI сравнивает модуль — по semver и для гейта `sim`: с новейшей опубликованной версией, по индексу новейшего релиза и её пакету; с папкой модуля в базе pull request; с папкой модуля на теге релиза, который опубликовал прошлую версию. `module-kit` оставил этот выбор `modules` (architecture 2.4 module-kit), а `sim` спрашивает, как CI узнаёт, что граф изменился (T03 в RUN.md `sim`);
  - где лежат снятия: `withdrawals.yaml` в корне; файл в папке модуля, который нарушил бы `module.layout`;
  - `paths` релиза: перечень по правилу поправки 2026-10-22 к R31 spec, без `.devcontainer/Dockerfile`; тот же перечень с Dockerfile, как у вида go. Перечня для `modules` в шаблоне architecture 3.3 .github нет: там только виды go и typescript;
  - `.gitattributes`: `modules/** -text`; `text eol=lf` на `LICENSE` и `NOTICE`.

### 3.4. Образцы в eval-наборе

Eval-набор модуля лежит в `eval/` его папки и в пакет не входит (раздел 3.1; R62 spec). Образцы в нём — трёх происхождений: синтетика, образцы взрослых добровольцев и образцы авторов (concepts 3 spec). Почему путь такой — R04.

Пока образцов добровольцев нет и быть не может. Страница образцов откроет назначение «eval-набор», только когда эпик E4 в RUN.md `spec` утвердит набор текстов — уведомление и форму согласия (R11 canvas). CONTRIBUTING `.github` таких образцов пока не принимает (раздел 4). Файл образца задаёт протокол eval: сообщение `Sample` пакета `novatrail.eval.v1`, один JSON на образец, без ключа задачи, с лицензией у образца eval-набора и с разметкой `markup`, а вырезки в нём — PNG в base64 (R93, R95 spec; [текст контрактов](../spec/contracts/README.md), раздел 11). Eval-набор модуля — каждый `.json` под его `eval/`, а раскладку внутри `eval/` протокол оставил `modules` ([текст контрактов](../spec/contracts/README.md), раздел 13). Раскладка — плоская: каждый образец — файл `eval/<id>.json`, где `<id>` — его ID, и в `eval/` нет ни папок, ни других файлов, кроме файлов и папок на `.` (подраздел 2.4; поправка 2026-11-06 к R04).

- **Роли:**
  - **доброволец** — взрослый, который пишет образец на странице образцов `canvas` по подписанной форме согласия;
  - **организатор eval-набора** — сопровождающий `modules`. Он принимает форму, получает файл, проверяет его и вносит;
  - **автор модуля** вносит свои образцы сам.
- **Путь образца добровольца:**
  1. До первого образца организатор принимает подписанную форму (R11 canvas; П-18). Форма лежит вне репозиториев, и агентов к ней не допускают (П-12). В ней:
     - заявление «мне 18 лет или больше»;
     - текст DCO 1.1 и заверение пункта (a);
     - публикация под Apache-2.0, которую нельзя отозвать (R20 spec; П-16);
     - прогоны у поставщиков ИИ в CI `modules` (R24 spec);
     - версия набора текстов.

     Окончательный текст формы пишет эпик E4 в RUN.md `spec` вместе с юристом (П-16; «Форма добровольца eval-набора в E4» у таблицы 2 RUN.md `spec`).
  2. Доброволец открывает страницу образцов и выбирает назначение «eval-набор». На ней он заявляет, что ему 18 лет или больше и что форма принята, пишет образец и сохраняет файл на своём устройстве (R09 и R11 canvas; architecture 3.6 canvas).
  3. Файл доходит до организатора каналом, который называет форма. Это не сервер платформы (architecture 3.2 spec) и не GitHub. Канал выбирает E4.
  4. Организатор проверяет файл — по таблице ниже, до того как файл попадёт в любую ветку. Файл, который не прошёл, не правится и не вносится: доброволец пишет образец заново.
  5. Запись о форме, вне репозитория, получает дайджест SHA-256 файла. По какой форме внесён каждый образец, знает организатор, а репозиторий — нет.
  6. Организатор кладёт файл в `eval/` модуля как `eval/<id>.json`, по ID образца, в ветке самого репозитория. Имя файла — ID образца, а содержание организатор не меняет: пункт (c) DCO держится, пока файл байт в байт тот, что заверил доброволец. Коммит он подписывает своим именем по пункту (c). Автор коммита — он же: проверка DCO сверяет подпись с автором (раздел 4). Ни `Co-authored-by`, ни данных добровольца нет ни в сообщении коммита, ни в имени ветки, ни в тексте pull request. Если есть образцы нескольких добровольцев, они идут одним коммитом, чтобы по коммиту не было видно, какие файлы от одного человека.
  7. Pull request проходит CI и мержится merge-коммитом (R30 spec). Пакета он не меняет и релиза не даёт: `eval/` нет ни в пакете, ни в `paths` (раздел 3.3).
- **Путь образца автора** — без формы и без организатора:
  1. Автор пишет образец на странице образцов с назначением «eval-набор» и сохраняет файл. Странице для этого нужно заявление автора, как у замера: его `canvas` вносит по R11 canvas, с протоколом eval (Д80 в таблице 4 RUN.md `spec`).
  2. Автор сам проверяет файл по таблице ниже, до push. Строка о форме к нему не относится.
  3. Он кладёт файл в `eval/` модуля, в ветке самого репозитория, и подписывает коммит своим именем по пункту (a) DCO. Подпись связана с образцом навсегда — пункт (d), — и это автор принимает, подписывая.
  4. Pull request — как в шаге 7.

  Автор без права записи вносит свои образцы как доброволец.
- **Синтетику** рисует код из зерна (R38 spec; R09 canvas): человека за ней нет, и формы ей не нужно. Её вносит автор или организатор, как свой образец: коммитом из ветки репозитория, со своей подписью DCO. Из таблицы к ней относятся строки о полях, схеме и PNG, а строки о форме и именах — нет.
- **Проверки до слияния:**

  | Что | Кто и когда | Чем |
  |---|---|---|
  | форма принята, а версия набора текстов в файле — её версия и утверждена | организатор, до push | запись о форме |
  | назначение — eval-набор; кто писал — взрослый, своим почерком или подражая детскому, а не ребёнок; кода писавшего нет; лицензия — Apache-2.0; разметка есть; задача — своего модуля | организатор, до push; с этапа 2 — eval-раннер. `sample-check` этих правил eval-набора не проверяет ([текст контрактов](../spec/contracts/README.md), раздел 13), и до этапа 2 их держат только руки — В16 в таблице 3 [RUN.md](../RUN.md), «в реестр spec» | поля файла (R93, R95 spec) |
  | на штрихах и вырезках нет имени, подписи, инициалов, школы и контактов, и в разметке тоже: тексты частей и истина сочинения публикуются с образцом | организатор, до push, глазами | просмотр образца без сети и без ИИ ([текст контрактов](../spec/contracts/README.md), раздел 11) |
  | у сочинения нет настоящих имён людей, а тема выдуманная (П-20) | то же | то же |
  | в файле только поля протокола: незнакомое поле — отказ. У PNG вырезок — только IHDR, IDAT и IEND, ни одного вспомогательного чанка: ни текста tEXt, iTXt и zTXt, ни метаданных eXIf, ни времени tIME, ни других. Имя файла не говорит о человеке | организатор, до push, и CI | протокол eval (R93 spec); спецификация PNG (раздел 4) |
  | файл лежит как `eval/<id>.json`, и `<id>` — его ID; в `eval/` нет ни папок, ни других файлов, кроме файлов и папок на `.` | CI, на каждом pull request, и с форка тоже | рецепт `modules`: правило раскладки, а не годности образца (поправка 2026-11-06 к R04) |
| файл — по протоколу eval, по правилам файла образца ([текст контрактов](../spec/contracts/README.md), раздел 11), каждый файл отдельно | CI, на каждом pull request, и с форка тоже | рецепт `spec` `just -f spec/justfile sample-check <файлы>`, без ключа, тем же кодом, что примеры `spec` (R93 spec; поправка 2026-11-06 к R04) |
  | задача образца — задача своего модуля, а дайджест её открытого вида — тот, что в образце; eval-раннер читает образцы и прогоняет их | CI, с этапа 2 | eval-раннер `tutor`, ключом платформы (R24 spec; R95 spec) |

  - Проверки без ключа CI гоняет на любом pull request, и с форка тоже.
  - Руками — до push: образец, который попал в ветку, уже опубликован, и убрать его из pull request может только Support GitHub (раздел 4). До проверки образец может нести имя, поэтому ни ИИ, ни агент его не смотрят (П-12).
- **Чего eval-набор не принимает:**
  - образец в pull request от добровольца или с форка: такой pull request не сливается и закрывается;
  - образец, который не прошёл проверку, — и исправленный организатором тоже: стёртые штрихи меняют образец, на котором стоит разметка;
  - работ учеников и образцов детей — никогда (concepts 3 spec; R25 spec).

  Если имя нашлось уже после мержа, образец уходит из `eval/` следующим pull request. Организатор просит Support GitHub убрать кешированные виды и ссылки pull request на коммит (раздел 4) и говорит обо всём добровольцу. Клоны и форки так не убрать — поэтому проверки и стоят до push.
- **Eval-раннер в CI** — с этапа 2 (R24 spec), только на pull request:
  - гоняет модули, у которых изменился `eval/` относительно базы pull request: опубликованного вида у eval-набора нет;
  - гоняет модули, у которых изменился пакет относительно опубликованного (раздел 3.2), — правка пакета меняет вердикт, — и новые модули;
  - гоняет все модули, когда pull request меняет тег `tutor`: с ним меняются промпты, модели и раннер. Переход на новую версию формата меняет пакеты всех модулей, но тем же pull request меняет и тег `tutor` (repositories 4 spec), так что раннер читает пакеты новой версии;
  - на push в `main` не гоняется: ветка перед мержем актуальна (R30 spec), и на `main` ложится то же дерево;
  - отдаёт отчёт — сообщение `Report` пакета `novatrail.eval.v1`, без содержания работ: только ID образцов, места, вердикты и отметки. CI `modules` читает его, а лог прогона с ответами моделей — свой у `tutor` ([текст контрактов](../spec/contracts/README.md), раздел 14; R95 spec). Может ли отчёт лежать в открытом логе CI, решают условия поставщика ИИ (Д97 в таблице 4 RUN.md `spec`) — это вопрос эпика E4.

  Цену прогона называют до первого запуска (R24 spec). Job с ключом на pull request с форка падает (R24 spec), а образцы и так приходят из ветки репозитория.
- **Что ждёт:**
  - `spec` — проверки правил eval-набора без ключа, до этапа 2 (В16 в таблице 3 [RUN.md](../RUN.md));
  - эпика E4 `spec` — текст формы, где лежат формы и записи о них, сколько хранятся, канал передачи файла и что делать с файлом, который не прошёл проверку («Форма добровольца eval-набора в E4» у таблицы 2 RUN.md `spec`);
  - `canvas` — заявление автора на странице и слова «передать файл организатору eval-набора» вместо pull request добровольца (Д80 в таблице 4 RUN.md `spec`);
  - чем организатор смотрит образец без сети и без ИИ: протокол eval инструмента не называет, и его выберет эпик E4 в таблице 2 [RUN.md](../RUN.md).

**Как решали** — подраздел 2.2 до итога детализации, дословно (R08). «Что известно» записано до решения, так что «решает `modules`» там говорит о дне записи, а ответ — в этом разделе.

- **Что известно:**
  - образец делается той же канвой, что у учеников. Он сохраняется файлом на устройстве добровольца и попадает в eval-набор через pull request в `modules`; на сервер платформы ничего не уходит (architecture 3.2 spec);
  - страница образцов к первому замеру решена: без хостинга, из релиза `canvas`, а образцы детей она делает без pull request — раздел 1 (R25 spec). Довод R25 spec против хостинга исходит из того, что pull request доброволец открывает сам, на GitHub;
  - рекомендация П-16 — письменное согласие на публикацию под лицензией модуля, с предупреждением, что отозвать его нельзя; на образцах — ни имён, ни подписей. Лицензия образцов — та же, что у модуля, Apache-2.0 (R20 spec);
  - eval-наборы первого среза — из образцов добровольцев: на них повторяют пороги чтения и цель оценки по рубрике, которые `tutor` поставил на синтетике и листах автора (дополнение 2026-10-28 к П-16; R67, R68, R71 spec). Если на образцах будет учиться своя модель чтения на устройстве, согласие называет и это (там же);
  - что лежит в образце со страницы образцов и как на него соглашаются — открытый вопрос П-18. Он исходит из того, что уже решил `canvas` (R09 canvas, R11 canvas): в образце eval-набора, который публикуется навсегда, — итоговая геометрия видимых штрихов, без времени, нажима и порядка написания. Согласие страница не берёт, а подписанную форму организатор принимает до первого образца;
  - у модуля сочинений образец — целый текст от руки. О чём модуль может просить писать ученика младше 18 — П-20, а образцы добровольцев для его eval-набора тоже публикуются навсегда (там же);
  - работы учеников в модуль не входят. Если их берут в eval, они лежат вне репозиториев и только с отдельного согласия (concepts 3 spec; П-10). Агенты разработки к ним доступа не получают, а образцы добровольцев лежат в модулях открыто (П-12);
  - eval-набор лежит в `eval/` папки модуля и в пакет не входит: eval-раннер берёт образцы из папки модуля в CI `modules` ([текст формата](../spec/format/README.md), раздел 10; R62 spec). Формат образцов — по протоколу eval из `spec` (R15 spec; architecture 3.2 spec). Протокол и формат образцов — эпик E3 в RUN.md `spec`, строка 1.6 [COORDINATION.md](../spec/COORDINATION.md);
  - pull request — это вклад, а каждый коммит вклада подписывается по DCO. Подпись публична навсегда, поэтому CONTRIBUTING разрешает подписываться адресом GitHub noreply (R22 spec). Подпись у каждого коммита pull request, кроме merge-коммитов, проверяет общая проверка DCO, и мерж она держит. Ruleset `main` разрешает только merge-коммит, так что коммиты pull request ложатся на `main` как есть (R30 spec);
  - eval-раннер `tutor` гоняет eval-набор модуля в CI с этапа 2 (architecture 3.10 spec) — ключом платформы у поставщика ИИ, и на pull request с форка его job падает, пока правку не перенесут в ветку репозитория (раздел 1; R24 spec; Т-28).
- **Варианты** (T02; первый в каждом пункте выбран, раздел 4 — источники):
  - кто вносит образец добровольца:
    - организатор eval-набора — сопровождающий `modules` — своим коммитом по пункту (c) DCO, а доброволец заверяет пункт (a) в форме;
    - доброволец сам, со своего аккаунта GitHub;
    - оба пути.

    Пункт (c) DCO годится, только если доброволец сам заверил пункт (a), а проверка DCO сверяет подпись с автором коммита. Аккаунт GitHub бывает с 13 лет, а push публикует сразу: убрать коммит из pull request, который на него ссылается, может только Support GitHub. П-18 спрашивает, как подпись DCO свяжет образец с аккаунтом, и называет вариант «мейнтейнер вносит сам, по пункту (c)». `canvas` оставил этот выбор T02 (R11 canvas);
  - где лежит согласие и что от него есть в репозитории:
    - форма вне репозиториев, в репозитории ничего, а запись о форме называет дайджесты внесённых по ней образцов;
    - форма вне репозиториев, а у образца в git — случайный номер формы.

    Кода писавшего у образца eval-набора нет (R09 canvas);
  - как проверить, что доброволец взрослый:
    - заявление «мне 18 лет или больше» в подписанной форме и на странице образцов (R11 canvas; П-6);
    - то же и документ, который смотрит организатор;
  - образцы авторов:
    - автор вносит свой образец сам, своей подписью DCO по пункту (a), без формы;
    - по форме, как образец добровольца;
  - кто и когда ищет имя на образце, — `canvas` оставил это T02 (architecture 3.5 canvas):
    - организатор, руками, до первого push;
    - ревью pull request;
    - ИИ или агент;
  - какие модули гоняет eval-раннер — T01 оставил это T02 (R03):
    - с изменённым `eval/` или пакетом, и все при новом теге `tutor`;
    - все на каждом pull request и на push в `main`.

**Как решали** — подраздел 2.4, дословно (R09).

- **Что известно:**
  - ID образца — 1–64 строчные латинские буквы, цифры и дефисы, «so that it can name the sample's file». У образца человека он случайный, а у синтетики выводится из зерна, так что одно зерно даёт один файл. Два образца одного набора ID не делят ([текст контрактов](../spec/contracts/README.md), разделы 11 и 13);
  - имя файла не должно говорить о человеке, а имя ему даёт организатор, не меняя содержания (R04; раздел 3.4);
  - образцы нескольких добровольцев идут одним коммитом, чтобы по коммиту не было видно, какие файлы от одного человека (R04);
  - pull request, который меняет открытый вид задачи, в нём же переделывает или убирает её образцы: раннер отвергает образец, чей дайджест открытого вида не совпал (R95 spec; поправка 2026-11-06 к R04);
  - образцов в `eval/` нет и до формы добровольца не будет, кроме синтетики и образцов авторов (раздел 3.4).
- **Варианты:**
  - плоско по ID образца — `eval/<id>.json`. Имя выводится из файла и о человеке не говорит, а раскладку нечем нарушить. Образцы задачи находят по полю задачи в файле или по отказу раннера, который их называет. Так рекомендовала строка В8, «в реестр spec», до протокола (R09);
  - по задаче — `eval/<id задачи>/<id>.json`. Образцы задачи, чей открытый вид меняет pull request, видны по папке, но путь повторяет поле файла и может с ним разойтись, и тогда нужна ещё проверка CI;
  - по происхождению — `eval/synthetic/`, `eval/volunteers/`, `eval/authors/`. Путь повторяет поле «кто писал» и делит образцы людей на группы, которые проще сопоставить между собой.
- **Рекомендация:** плоско, `eval/<id>.json`, а CI сверяет, что имя файла — его ID: ни одно поле файла путь не повторяет, кроме ID, и проверка одна. Образцы задачи, чей открытый вид меняет pull request, CI называет и так — отказом раннера.

### 3.6. Первая пачка

Первая пачка `novatrail/olympiad-math` — 27 задач standalone на три полосы и 9 уроков, для первого приложения, где автор локально решает задачи в браузере (R76 spec). Почему так — R07. Задачи и уроки — по таблице раздела 3.5 и по этому разделу. Файлы модуля пишет эпик содержания, строка 3.6 [COORDINATION.md](../spec/COORDINATION.md). Список посчитан по standalone 89986bc и тексту формата 0.2 (раздел 4), а пишется пачка в формате 0.3: он меняет Starlark, сравнение версий и индекс, а у пачки нет ни шаблонов, ни условий, так что список тот же (R101 spec; R09).

- **Навыки** — `counting-gaps`, `combinatorics-enumeration` и `pigeonhole-basic`. Эти три темы standalone идут на всех трёх полосах, ответы у них почти везде целые числа, а у страницы темы сайта — по примеру на каждый уровень. Задач с ответом-числом, без «Which of these…» и без картинки у них 52, 64 и 63 из 65.
- **Правило выбора:**
  1. годная задача — у неё верный вариант целое число, с единицей или без, как «50 m», а вопрос не указывает на варианты. Картинки у неё нет, кроме картинки `row` по пункту 5. Ответ с единицей пишется так же, как без неё: ключ — число, а единица — в `units` (раздел 3.5);
  2. на каждый навык и полосу берутся три задачи — сложности 1, 3 и 5;
  3. на каждой сложности берётся первая годная задача по ID, если её пояснения неверных вариантов ключа не называют, а если такой нет — первая годная. Задача не берётся, если её ключ:
     - стоит в тексте её урока — `lesson.no-leaks`;
     - стоит в условии более ранней задачи урока;
     - равен ключу более ранней задачи урока: её решение кончается её ключом, а урок не должен называть задач, тексты одной из которых дают ответ другой ([текст формата](../spec/format/README.md), раздел 20).

     Если годной задачи на этой сложности нет, берётся ближайшая сложность, сначала выше;
  4. ключ в тексте ищется правилом поиска чисел формата ([текст формата](../spec/format/README.md), раздел 20): по значению, так что `7` есть в «7 rungs», но не в «17»;
  5. у `counting-gaps` на полосах 1–2 и 3–4 одна задача из трёх — с картинкой `row`: на первой сложности, где такая годна, она берётся вместо задачи без картинки. Годных задач с `row` — 10, все на этих двух полосах.

  Сложность сдвинулась у одной задачи: у `counting-gaps` 1–2 ключи годных задач сложности 1 стоят в тексте урока, и взята `gaps-12-d2-1`.

  В трёх уроках число из решения или из пояснения варианта более ранней задачи равно ключу более поздней:
  - `enum-56-d1-1` → `enum-56-d3-2`, 16 — в решении и в пояснениях вариантов 36 и 576;

### 3.8. Набор школьной математики 3 класса

Набор `novatrail/grade-3-math` — небольшой модуль на рабочей тетради, которым `modules` проверяет формат на второй канве, до T38 `spec` (R41 spec). Первое приложение его не ждёт: «другие модули» в него не входят (COORDINATION.md `spec`). Почему так — R15.

- **Паспорт, граф и каталоги** — записи примеров формата `school-math-grade-3` дословно, кроме ID — `novatrail/grade-3-math` (R03). Аудитория — `under_13`, класс 3, одна полоса `grade-3`, язык объяснений — `en`, без `dependencies`.
- **Навыки** — четыре навыка примера, замкнутые по пререквизитам:

  | Навык | Пререквизит | Ярус | Учит навыку-опоре |
  |---|---|---|---|
  | `times-tables` | — | 1 | `core.multiplication-table` |
  | `division-with-remainder` | `times-tables` | 2 | `core.division-with-remainder` |
  | `fractions-of-a-whole` | `times-tables` | 2 | `core.fractions-of-a-whole` |
  | `comparing-fractions` | `fractions-of-a-whole` | 3 | — |

  Граф — не цепочка, так что модуль не последовательный ([текст формата](../spec/format/README.md), раздел 21).
- **Ловушки** — 11:
  - три из примера дословно;
  - `wrong-operation` из примера, но с другими словами: её ловят и строки без истории;
  - `reversed-comparison` из примера, но с навыком `comparing-fractions`: навыка примера `numbers-to-1000` в наборе нет (`traps.known-skills`);
  - шесть своих — `took-away`, `remainder-left-out`, `remainder-not-added`, `top-and-bottom-swapped`, `one-part-only` и `greater-bottom-greater-fraction`.

  **Приёмы** — три из примера и свой `draw-the-parts`. **Шаги решения** — два шага примера.
- **Задачи** — 12 страниц `tasks/<навык>-d<сложность>.yaml`, сложности 1, 3 и 5, по 6–10 строк:

  | Навык | Строки | Виды проверки |
  |---|---|---|
  | `times-tables` | окошко где угодно в строке: множитель, делимое, произведение, частное; на d5 — истории с `units` | `number` |
  | `division-with-remainder` | «47 ÷ 6 = [ ] r [ ]» — две ячейки в строке; на d5 — истории с двумя окошками, остаток, которому нужно место, и пропущенное делимое | `number` |
  | `fractions-of-a-whole` | доля по равным частям, `form: any`; доля числа; несократимая дробь, `form: reduced` | `fraction`, `number` |
  | `comparing-fractions` | знак между двумя дробями с одним знаменателем или одним числителем; на d5 — бо́льшая или меньшая из двух дробей | `choice` от руки — `<`, `>` и `=`, — `fraction` |

  - Условие страницы называет форму ответа: «in lowest terms», «Write <, > or =».
  - Решение — абзац на строку. У строк — значения ловушек с текстами без чисел, и одна ошибка — одно значение ловушки: у строки деления его несёт только ячейка частного.
  - `simpler_case` — только у историй, на меньших числах. Ни написанное в нём, ни то, что из него выходит, не ключ своей строки, а доли не называют ключей страницы и словами.
  - Строка не повторяет факта из текста своей страницы или из решения ранней страницы того же урока.
  - `givens` и `unknown` нет: шаги решения их не дают.
  - Картинок, `predicate` и шаблонов нет.
- **Уроки** — по уроку на навык, `lessons/<навык>.yaml`: объяснение, затем три страницы по возрастанию сложности. В текстах уроков, ловушек и приёмов нет цифр: ключи страниц — малые числа, а проверка утечки ищет их во всех этих текстах ([текст формата](../spec/format/README.md), раздел 20). Знаков сравнения там тоже нет, хотя их проверка не ищет: условие страницы называет все три знака, а ключ, который стоит в тексте, видном вместе с пунктом, не ищется (там же; R15). Разобранного примера нет: в формате 0.3 он бывает только на листе ([текст формата](../spec/format/README.md), раздел 21).
- **Страница встаёт.** Каждая из 12 страниц прошла раскладку `canvas` v0.1.2 — его `pageOf` — и занимает от 3 до 7 рядов. Правила страницы в 0.3 нет, есть только ориентир — до 10 рядов ([текст формата](../spec/format/README.md), раздел 14; поправка 2026-11-01 к R51 spec). Источник — раздел 4.
- **`LICENSE`** — текст Apache-2.0. `NOTICE` нет: тексты свои.
