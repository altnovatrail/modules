# Decision log of modules

> Why modules is built the way it is. Each entry: what was decided, why, what was rejected, and in its tail "— *Consequence:*" the files, by their paths, that a change of it edits.
>
> **Rule:** do not propose again what was rejected without new facts. If a decision has to change, ask the author and rewrite its entry in its place, and every entry the change touches: an entry is its text in force — what was decided, why, what was rejected and what a change of it edits —, git keeps the old text, and the commit says why. An entry's number stands in its heading alone: an entry cites no other entry and no section, says in words what it rests on, and carries no date of who decided it and no amendment; a fact that no run of ours checks cites its one record of [sources.md](sources.md).
>

## The layout of the repository and the releases

**R03. The modules' folders lie in `modules/<name>/`, where `<name>` is the second half of the module ID `novatrail/<name>`: `olympiad-math`, `grade-3-math`, `english-essays` and `check-board`. CI checks all the modules on every pull request and compares each with its published versions — by the index of the newest release and their packages. A release builds the packages of all the modules, and carries the cumulative index and only the versions that it publishes itself — as an archive `sha256-<hex>.tar.gz` per package. The withdrawals lie in `withdrawals.yaml` at the root.**
- **The repository's tree:**
  - the module's folder is `modules/<name>/`, and `<name>` is the second half of its ID: the module `novatrail/olympiad-math` lies in `modules/olympiad-math/`. Inside is the module layout by the [format text](../spec/format/README.md), which left to `modules` where the folder lies and what it is called;

The IDs of these modules are `novatrail/olympiad-math`, `novatrail/grade-3-math` and `novatrail/english-essays`: kebab-case starting with a letter, as the form `module_id` requires. The name names the subject and the audience, not the explanation language: the explanation languages of the slice are О-2, and it is open. A module in another explanation language is another module, by the format, and its name will get a suffix with a BCP 47 tag, for example `olympiad-math-en`;
  - `check-board` — the module `novatrail/check-board` of the check board of `tutor`. Its name names the board whose tasks it holds, not a subject and an audience: the rule of the names is for the modules of the slice, and this module stands beside them, not among them. It is in Russian and has no twin in another explanation language, so its name has no suffix of a language. CI and the release take the folder as they take every folder of `modules/`;
  - at the root — the list of withdrawals `withdrawals.yaml`, from the first withdrawal on (below), the README and the `LICENSE` of the repository. The folder of each module has its own `LICENSE` too;
  - `.gitattributes` is `modules/** -text`: git converts the line endings of no file of the modules, neither at a commit nor at a checkout ([gitattributes of git 2.56.1](https://github.com/git/git/blob/v2.56.1/Documentation/gitattributes.adoc)). The package carries `LICENSE`, `NOTICE` and the media files byte for byte, and a conversion to CR LF would change the package digest. `spec` protects `format/` the same way — `format/** -text`.
- **CI:**
  - every pull request and push to `main` checks all the modules, not only the changed ones. The CLI of `module-kit` checks each folder `modules/*/`. CI checks the tree — in `modules/` only the modules' folders, and the ID of each is `novatrail/<folder>` — and builds the package of each module. So a new tag of `spec` or of `module-kit` re-checks all the modules without a special rule;
  - **the CLI is pinned in one place** — in the `toolchain` stage of `.devcontainer/Dockerfile`: the release binary of `module-kit` at an exact tag and sha256 sum. The same binary is taken both by CI and by the recipe `release-files` on a release (below), so CI checks the modules with the same version of the CLI that the release will build them with. The binary's signature is checked by the recipe `release-verify` in CI of each pull request and push to `main`, before CI checks the modules with it. The first run of the binary is `module-kit --version` at the build of the image, and before it the signature is held by a chain: `SHA256SUMS`, checked by `release-verify` before the sums are written into `ARG`, and the sum, which the build checks before the run. From then on the sum holds the binary. How the CLI stands in the `toolchain` stage and how CI calls it, as a difference of the container from the container of `spec`, is a decision of its own;
  - **the comparison with what is published.** CI takes the `module-index.json` of the newest release of `modules` and checks its signature with the recipe `release-verify`. For each module:
    - if its version is already in the index, the digest of the package that CI built matches the digest of the entry. Otherwise the content was edited without raising the version, and the release would refuse by the format's rule `module-index.one-package` already after the merge;
    - if the version is new, it is above each published version of the module, withdrawn ones too: a version is published once, and one line of versions lives in a module's folder. The CLI of `module-kit`, by its command `diff`, compares the new version by the rules of semver with each published version of the module, withdrawn ones too, and across a format transition too. CI downloads the package of each from the release that its entry names and checks it by the chain of digests from the checked index;
    - across a format transition — and while the format is v0, this happens after each of its transitions — `diff` reads the package of a version written in another format version by the places that the format keeps in all versions: in the inventory, in the names of the package's files and in the canonical view — the languages, the bands, the skills and `retired_skills`, the keys of the tasks, lessons, traps and techniques. The rules about skills, `retired_skills` and IDs go across a transition too, and the version part, while the format is v0, is major. Which rules compare with each published version and which with the newest, the format says;
    - before the first release there is no index, and all the versions are new;
  - **the form of the call** of the CLI's commands `index` and `diff` is the one that `module-kit`'s `docs/architecture.md` gives: the recipes of `modules` follow it and check the call with their tests;
  - **the gate of `sim`** runs in CI, in the job "Gate", on every pull request and push to `main`. CI runs `sim` when what the simulator reads from the package has changed — whether it has changed is decided by `sim` itself with its command "has it changed", for a new module too, — on the pull request's package that CI built, with invariants and absolute thresholds, without bands. A pull request that changes the tag of `sim` runs the simulator on all the modules. `sim` reads the server part by the types of the canonical view, without `module-kit`. The releases up to v0.2.8 came out without the gate: the first tags of `sim`, up to v0.1.8, refused `olympiad-math` 0.3.0;
  - **a format transition goes without `sim`.** If the previous version of a module is written in another format version, the simulator is not run in this pull request: `sim` at its former tag will not read the package of the new format version. In a format transition `modules` changes nothing of what the simulator reads from the package — neither the graph nor the tasks' bindings — except the writing itself in the new format version, and the review of `modules` holds this, not CI. All of that is changed by a separate pull request once `sim` has moved to the new format version, with the simulator;
  - what to run is decided inside the job, not by a filter `paths` on the workflow: the checks of a workflow that a filter skipped hang "Pending", and a required one holds the merge ([GitHub Docs, the filter `paths`](https://github.com/github/docs/blob/e0b0c90/data/reusables/actions/workflows/triggering-a-workflow-paths2.md));
  - which modules the eval runner of `tutor` runs, from stage 2, is decided with the samples of the eval set: the eval set does not go into the package, and the comparison of packages does not see its changes.
- **The release:**
  - `release.yml` is by the release template of `.github`, with the input `previous-file: module-index.json` from the first release. The shared `release.yml` has this input since v0.1.14 ([the architecture of `.github` v0.1.15](https://github.com/altnovatrail/.github/blob/v0.1.15/docs/architecture.md));
  - the recipe `release-files VERSION PREVIOUS` runs in the container of the `toolchain` stage, on the commit's tree without git, without submodules and without the network. The CLI of `module-kit` in it is the same binary from the `toolchain` stage as CI's (above);
  - the recipe builds the packages of all the modules and the index: from the previous index, checked by the shared release, its own packages, the tag VERSION and `withdrawals.yaml`. For the first release the shared release gives an empty string instead of a path, and the recipe tells the build that there is no previous index. One may build all the modules or only the changed ones, but the recipe cannot even learn which have changed: there is no git in its tree. And building all of them on a release catches once more an edit without raising the version, with the refusal `module-index.one-package`;
  - into `dist/` the recipe puts:
    - `module-index.json`;
    - `LICENSE` — the text of Apache-2.0 from the root, as in a release of `module-kit`;
    - an archive for each package whose entry names the tag VERSION — that is, only for the versions that this release publishes. The package of a version that the index already named lies in the release that its entry names, and does not come out a second time.

    The bundle `.sigstore.json` for each file is put by the shared release. A release that only withdraws versions carries the index and `LICENSE`;
  - **the archive of a package** is named by the package digest, with `:` replaced by `-`, with `.tar.gz`: `sha256-<64 hexadecimal digits>.tar.gz`. Inside is the package as files, at the root of the archive, without a top folder: `inventory.json`, `server.json`, `device.json` and `device/` with `LICENSE`, `NOTICE` and `media/<path>`. Apart from these files and their folders, there is nothing in the archive — neither links nor other entries. The archive's address is derived from the index's entry — the tag `release` and `package_digest`: `https://github.com/altnovatrail/modules/releases/download/<release>/sha256-<hex>.tar.gz`. It is read at the public address, without a token and without the REST API. Nothing holds the bytes of the archive itself, and nothing needs to: a reader checks the inventory against the package digest, the parts against the inventory, and the files against the list of the device part, and takes only the paths that this list names, as the format requires;
  - **the withdrawals** are `withdrawals.yaml`: YAML by the format's rules for it, and the form is `$defs/withdrawals` of the index's schema, `module-index.schema.json`, to which the member `withdrawals` of the index vector refers too: module ID → version → withdrawal reason. The form requires at least one entry, so there is no file while nothing is withdrawn: then the recipe tells the build that there are no withdrawals. With the first withdrawal the file appears and from then on only grows: a repeat of a withdrawal with the same reason changes nothing;
  - **the fix of a withdrawn version.** A withdrawn newest version of a module is fixed by a version above it by semver, and which part to raise the rules of semver decide. A change of a published task's key is major, so the fix of a version withdrawn by `wrong_key` is the next major. A fix that is ready goes in the same pull request as the withdrawal and comes out in the same release: a version that comes out in this release can be withdrawn too. The withdrawal does not wait for the fix. A version older than the newest cannot be fixed: a new version is above all the published ones (above), and a fix comes out only as a new version of the newest line;
  - **`paths`** holds what the release is built from and what the consumer will get. The list of the kind `modules` is kept by the release template of `.github`, with the reason why it has no `.devcontainer/Dockerfile`, and [architecture.md](architecture.md) refers to it. Until the template carries it, [architecture.md](architecture.md) holds the list that the template will get and `release.yml` carries the same; where they diverge, the template is right. The list holds the modules' folders without their `eval/`, `withdrawals.yaml`, `justfile`, the root `LICENSE` and `release.yml`, and not `.devcontainer/Dockerfile`.

    A trial on 2026-11-02, git 2.56.0, in a temporary repository. `git diff --name-only` with this list found a change of a module's `manifest.yaml`, task, lesson, `LICENSE`, `NOTICE` and `modules/a/media/eval/p.png`, of `withdrawals.yaml`, `justfile`, the root `LICENSE` and `release.yml`. It did not find a change of a module's `eval/`, of `docs/`, `RUN.md`, `README.md`, `ci.yml` and `.devcontainer/Dockerfile`, and `git diff --quiet` after a commit with only them returned 0 — no release. The magic `glob` is needed because without it `*` in a pathspec matches `/` too: `modules/*/eval/*` would exclude a module's `media/eval/` too;
  - **the tag that CI of `canvas` takes** is the `vX.Y.Z` of a release of `modules`: the number of the repository itself, not a module's version. CI of `canvas` reads the index of this release at an exact tag and takes the packages from the releases that its entries name. The index of the newest release it reads only for the withdrawal marks;
  - releases are not deleted or rewritten: immutable releases are a condition of the signature check, and a verdict is repeated on old packages.

— *Why:*
- **`modules/<name>/`**: the root holds the service files, and the rule "a folder in `modules/` is a module" is checked without exceptions. The format's index vectors lay out a release's modules the same way — `modules/<name>/`. There is no publisher in the path: only the official modules lie here, and third-party ones will come with the registry service (О-9).
- **The names**: an ID is forever, since the full IDs of skills and tasks — `novatrail/olympiad-math/skill/…` — are kept by the learner model and the progress. A language in the name would decide О-2 before it is itself decided.
- **The archive by digest**: the name is derived from the index's entry — each has a digest, no replacement of `/` is needed, and two names will not collide. The build of the image of `api` needs only the packages of the window, and it wants to take them by the entry, without going through the release's files ([row В6 of the questions of `api` at d409351](https://github.com/altnovatrail/api/blob/d409351/RUN.md)). The release files are a flat list with safe names, and the media paths have `/`: a package as loose files would not fit into a release without a renaming of its own, and a release has no more than 1000 files (sources 2.1).
- **Only the new versions**: an entry names one release, and no entry would name the copies of a package in later releases.
- **The comparison with what is published**: CI catches before the merge exactly what the release would later refuse on, and takes the previous versions where the consumers take them — from immutable releases. One line of versions and a comparison on every pull request would give the same by induction as a comparison with each published version, but only while each published version has itself passed the comparison, and `module-kit` compares with each. Across a format transition `diff` compares too: the rule "no entry has gone" holds only the skills, and the IDs of tasks, lessons, traps and techniques have no table of their own.
- **The gate by what `sim` reads**: a gate by the graph alone would let through a pull request that reweighs the tasks or changes their bindings without touching the graph, since `sim` and `engine` read the tasks too. Whether it has changed is decided by `sim`: it knows what it reads, and a copy of this rule in `modules` would diverge from it. Without bands, since the pull request's package has no base to compare them with. In a format transition review holds all of what the simulator reads, not only the graph: a transition that reweighs the tasks or changes their bindings without touching the graph would otherwise come out in a release without the simulator.
- **All the modules on every pull request**: there are few of them, and a rule "which one has changed" would save nothing for the check. A new tag of a tool requires checking them all anyway.
- **One binary of the CLI for CI and the release**: two places where the version is pinned diverge, and then CI would let through modules that the release will reject after the merge. Its signature on every run is one check for all, without a rule "have the `ARG` changed" and its tests.
- **The Dockerfile is not in `paths`**: the package and the index depend only on the files of the module and the format version of its module manifest, not on the version of `module-kit`. Raising the CLI would give a release with the same index, and the Dockerfile changes every week: Dependabot proposes the base image (`.github/dependabot.yml`, `docker`, `weekly`). A new format version changes the modules' manifests, and they are in the list. The price is the whole `justfile` in the list, though it also holds the CI recipes: a change of them will give a release with the same index, as for the kind go. This is a rare change, and the recipe `release-files` is in the `justfile` too.
- **`-text` on the whole of `modules/`**: the package digest is taken of `LICENSE`, `NOTICE` and the media files byte for byte.

— *Rejected:*
- the modules' folders at the root, `<name>/`: the root would mix the modules with the service folders, and the rule "a folder is a module" would need exceptions;
- `modules/novatrail/<name>/`: an extra level for the sake of publishers that will not be here (О-9);
- the names `school-math-3` and `short-essays`: the second does not say that the essays are in English;
- the names `school-math-grade-3` and `essays-in-english`: each full ID is longer without new clarity;
- names with the explanation language, `olympiad-math-ru`: they would decide О-2 before it is itself decided;
- an archive by ID and version, `novatrail+olympiad-math+1.2.0.tar.gz`: the name is held by a replacement rule, not by the content;
- the packages of all the current versions in each release: copies that no entry names;
- a package as loose files in a release — the argument above;
- one archive for all the packages of a release: the build of the image of `api` takes only the packages of the window ([row В6 of the questions of `api` at d409351](https://github.com/altnovatrail/api/blob/d409351/RUN.md));
- a comparison with the pull request's base in git: an edit of a published version would be caught only by the release's refusal, after the merge;
- a comparison with the module's folder at the release's tag in git: CI would need the whole history, and the link of the folder with the published package would have to be checked by a rebuild;
- a comparison only with the newest published version — the argument above. The price of the chosen option is the archive of each published version of the module in each pull request that raises this module's version;
- across a format transition, only a check that the version has grown, with review holding the skills — the argument above;
- checking only the changed modules in CI — the argument above;
- a filter `paths` on the CI workflow: a required check would hang "Pending";
- the withdrawals in the module's folder: such a file would break `module.layout`, and a module does not see a file starting with `.`;
- the fix of a withdrawn version as the next version of the same major: a change of the key is major;
- `.devcontainer/Dockerfile` in `paths`, as for the kind go: raising `module-kit` and a new base image would give releases equal to the previous one;
- the list of `paths` only in [architecture.md](architecture.md), apart from the release template of `.github`: the template keeps the lists of the kinds, and there is no new fact against keeping this one there;
- the CLI in CI at a tag of its own, and in the recipe from the Dockerfile: two versions of the CLI could diverge — the argument above;
- the signature of the CLI checked only on a pull request that changes its tag and sum: the rule "changed", with the base of the pull request and the first parent on a push, would have to be written and tested;
- the gate of `sim` by the graph alone — the argument above; an own check "has it changed" in CI of `modules` by the canonical view — a second place for the rule of `sim`; the graph and the tasks' bindings without the rest of what the simulator reads — a boundary that `modules` would draw for `sim`;
- running `sim` in a format transition: `sim` at its former tag will not read the package of the new version; a transition that waits for a tag of `sim` that reads the new format version and goes with the simulator — each format transition would stand still until that tag; review that holds only the graph in a transition — the argument above;
- `text eol=lf` instead of `-text`: the attribute `text` turns on the conversion of line endings for the media files too, and the PNG signature has the bytes `0D 0A` ([gitattributes of git 2.56.1](https://github.com/git/git/blob/v2.56.1/Documentation/gitattributes.adoc)). On `LICENSE` and `NOTICE` alone it would work, but `-text` holds everything byte for byte, as in `spec`.

— *Consequence:* `.gitattributes`; `withdrawals.yaml`; `justfile`; `.github/workflows/ci.yml`; `.github/workflows/release.yml`; `.devcontainer/Dockerfile`; [architecture.md](architecture.md).

## Samples in the eval set

**R04. An adult volunteer's sample is added to the eval set by the eval-set organizer — a maintainer of `modules`. The organizer accepts the signed consent form, gets the file, checks it by hand before the first push and brings a pull request from a branch of the repository itself. The organizer signs off the commit with their own name under clause (c) of the DCO, and the volunteer certifies clause (a) in the form. The form lies outside the repositories, and nothing of it is in the repository. That the volunteer is an adult is said by their declaration in the form. A module's author adds their own sample themselves, under the same form, which they sign and accept themselves, as the organizer, with their own DCO sign-off. The sample file is by the eval protocol of `spec`, and the layout of `eval/` is flat, `eval/<id>.json`, with nothing starting with `.`. A session of Claude Code here reads no person's sample.** The eval runner comes from stage 2. Volunteers' samples come only once `spec` has approved the texts of consent: until then the samples page does not open the purpose «eval-набор» ("eval set") ([the decision log of `canvas` at 5cd33ce](https://github.com/altnovatrail/canvas/blob/5cd33ce/docs/decisions.md)).
- **The path** — step by step in [architecture.md](architecture.md), and only there. Its rules:
  - the organizer accepts the form before the first sample ([the architecture of `canvas` at 5cd33ce](https://github.com/altnovatrail/canvas/blob/5cd33ce/docs/architecture.md)), gets the file by the channel that the form names, and checks it before the file gets into any branch. The channel is not the platform's server and not GitHub;
  - a file that did not pass the check is not edited and not added: the volunteer writes the sample anew;
  - in git and on GitHub — only the organizer. The organizer is the commit's author and its sign-off, and neither `Co-authored-by` nor the volunteer's data are in the commit's message, the branch's name or the pull request's text. The volunteer needs no GitHub account;
  - the samples of several volunteers, if there are any, go in one commit: the commit does not show which files come from one person;
  - a pull request with a sample from a volunteer or from a fork is not merged.
- **DCO.** Clause (c) is "The contribution was provided directly to me by some other person who certified (a), (b) or (c) and I have not modified it" (sources 3.2). So the form carries the text of DCO 1.1, and the volunteer certifies clause (a) in it. The organizer gives the file its name and does not change the content: clause (c) holds while the file is byte for byte the one the volunteer certified. The DCO check checks the sign-off against the commit's author ([`dco.yml` of `.github` v0.1.15](https://github.com/altnovatrail/.github/blob/v0.1.15/.github/workflows/dco.yml)), so the commit's author is the one who signed off.
- **The consent** is the signed form, and it lies outside the repositories, with the organizer. Agents are not let near it, as they are not let near eval samples outside the repositories. The link with the samples goes from its side: the record of the form names the SHA-256 digests of the files added under it. In the repository there is nothing of the form — neither a name, nor a number, nor a code. What the form carries, its text, where the forms and their records lie, how long they are kept, by which channel the file goes and what happens to a file that did not pass the check, `spec` decides with the volunteers' consent.
- **An adult** — by the declaration "I am 18 or older" in the signed form. The volunteer makes the same declaration on the samples page ([the architecture of `canvas` at 5cd33ce](https://github.com/altnovatrail/canvas/blob/5cd33ce/docs/architecture.md)). Whether the declaration is enough in every country, П-18 asks the lawyer.
- **An author's sample** passes the same checks, under the same form of the eval-set volunteer: the author signs it and accepts it themselves, as the organizer. An author with write access adds their sample themselves, with their own DCO sign-off under clause (a). An author without write access adds their samples as a volunteer. The steps are in [architecture.md](architecture.md).
- **The checks** — by the hands of whoever adds the sample, before the first push, without AI and without agents; CI repeats them without a key (below). The list is in [architecture.md](architecture.md).
- **The sample file** is the message `Sample` of the package `novatrail.eval.v1` of the [contracts text](../spec/contracts/README.md): one JSON per sample, without the task's key, with a license for an eval-set sample and with the markup `markup`. A reader reads it strictly: an unknown field is a refusal. The PNG of the crops has only IHDR, IDAT and IEND, not one ancillary chunk.
- **The check without a key** is the recipe of `spec` through the submodule, `just -f spec/justfile sample-check <files>`, in the `toolchain` stage: the same code that checks the examples of `spec`. `modules` writes no check of its own. CI runs the recipe on every sample file of the eval set, and on a pull request from a fork too. The rules of validity are one for the samples page, the runner and CI. The recipe checks each file by the rules of the sample file; the rules of the eval set — the purpose «eval-набор» ("eval set"), the markup, a task of its own module, not a child, IDs without repeats — `modules` does not check by a recipe of its own either, but asks `spec` for them, and the recipe's mode for a module's eval set holds them.
- **A module's eval set** is each file under its `eval/` whose name ends in `.json`, and each is a sample of a task of its own module. The layout inside `eval/` the protocol left to `modules`.
- **The layout is flat:** a sample is a file `eval/<id>.json`, where `<id>` is the sample's field `id`, and in `eval/` there are neither folders, nor other files, nor anything starting with `.`, at any depth: neither a file nor a folder. The organizer does not choose the name: the name is the sample's ID. CI checks the layout, and that the file's name is the ID of its sample, by a recipe of its own, `just eval-check`: this is a rule of the layout of `modules`, not a rule of the sample's validity, which `sample-check` holds. So two samples of a set do not share an ID either: one folder has no two files with one name.
- **A sample and an edit of the task.** The eval runner takes the task from the package that `module-kit` built on the pull request's commit, and rejects a sample whose digest of the task's open view did not match — then the run does not pass. So a pull request that changes a task's open view remakes or removes its samples in the same pull request. A volunteer's sample the organizer does not remake: clause (c) of the DCO holds while the file is byte for byte the one the volunteer certified. The organizer removes the sample or asks the volunteer to write it anew.
- **The ban on reading.** `.claude/settings.json` forbids a session of Claude Code in this repository to read `modules/*/eval/*`, except `synthetic-*.json`, and any file of `eval/` in an epic's clone of `modules`, which every NovaTrail container reads by its absolute path under `/workspaces/.epics`:

  ```json
  "deny": [
    "Read(modules/*/eval/*)",
    "Read(!modules/*/eval/synthetic-*.json)",
    "Read(//workspaces/.epics/*/modules/modules/*/eval/*)"
  ]
  ```

  - The last rule is spec's template's: a `!` carves out of the relative rules before it alone, and is read relative to the current folder even before `//` ([Configure permissions](https://code.claude.com/docs/en/permissions.md), read 2026-11-27), so in a clone in `.epics` the synthetic samples are closed too.

  - Claude Code's path rules follow the gitignore syntax. A rule with `!` is a negation, and it cuts paths out of the `deny` rules of the same file before it; the order of the rules is deny, ask, allow, and allow makes no exception from deny (the documentation of Claude Code, [Configure permissions](https://code.claude.com/docs/en/permissions.md), read 2026-11-11). A negation does not reach files inside a folder that a rule before it forbids whole, so a folder in `eval/` is closed entirely — the layout rejects it anyway.
  - The ban holds for the tools for reading files and for the Bash commands that name the file — "`cat`, `head`, `tail`, `sed`, and `tee`" — and for redirections. But not for a program that opens files by itself, "like a Python or Node script", and not for `grep -r` without a file's name (ibid.). So a person's sample lies in the working copy only while the author adds it, and the session looks only at CI's output.
  - Checked in a session of Claude Code: `Read` of the stub file `modules/grade-3-math/eval/person-stub.json` — `{"id": "person-stub"}`, without anyone's data — was refused, "File is in a directory that is denied by your permission settings", and so were `cat` and `jq -r .id` with its name; `Read` of `synthetic-4.json` passed. The stub was removed.
- **The name.** The ban tells samples apart by name, and the name is the sample's ID. A synthetic sample's ID is `synthetic-<seed>`, and a person's is random, and `canvas` does not name its shape. So `just eval-match` rejects a person's sample with an ID starting with `synthetic-`: a session could read such a file. The refusal is 1, the test is `test/eval-match.test.mjs`.
- **The eval runner in CI** — from stage 2, only on a pull request:
  - runs the modules whose `eval/` has changed against the pull request's base or whose package has changed against the published one, as CI compares it, new ones among them;
  - runs all the modules when a pull request changes the tag of `tutor`. A move to a new version of the format changes the packages of all modules, but the same pull request also changes the tag of `tutor`. The admission of a new model is such a pull request: it moves to the tag of `tutor` with this model and runs the eval sets of all the modules, and `api` takes this tag only after its merge;
  - does not run on a push to `main`. The price of a run is named before the first launch.

— *Why:*
- **The organizer adds it.**
  - A push publishes. A branch of a public repository is seen at once, and after a rewritten history the commits remain "Through any pull requests that reference them" ([GitHub Docs, Removing sensitive data from a repository](https://github.com/github/docs/blob/e0b0c90/content/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository.md)). A name on a sample must be found before publication, not at the review of the pull request.
  - The DCO sign-off and the pull request's author tie the sample to an account forever: clause (d) of the DCO, and the merge only by a merge commit.
  - A GitHub account is allowed from age 13 (sources 2.4) and does not say whether its owner is an adult. The form would have to be tied to the account.
  - On a pull request from a branch of the repository the eval job with a key does its work, and on a fork it fails, and a maintainer moves the change anyway.
  - The organizer accepts the form, so everything that knows the volunteer's name stays with one person.
- **No trace in the repository.** A number of the form on a sample would tie together the published samples of one person, and it is for this that `canvas` removed the writer code from the eval-set sample ([the decision log of `canvas` at 5cd33ce](https://github.com/altnovatrail/canvas/blob/5cd33ce/docs/decisions.md)). The digest in the record of the form gives the same link, but only to whoever has the form. A commit that holds the samples of one person and only them would tie them the same way, so the samples of several volunteers go in one commit.
- **The declaration**: so П-6 advised, and so `canvas` decided ([the decision log of `canvas` at 5cd33ce](https://github.com/altnovatrail/canvas/blob/5cd33ce/docs/decisions.md)). A document with the date of birth is extra data, and nothing can be recorded from it anyway.
- **An author's sample under a form**: the samples page of `canvas` for the purpose «eval-набор» ("eval set") requires two declarations, «мне 18 лет или больше…» and «форма согласия версии … подписана и принята организатором» ("the consent form of version … is signed and accepted by the organizer") ([the architecture of `canvas` at 5cd33ce](https://github.com/altnovatrail/canvas/blob/5cd33ce/docs/architecture.md)), and has no declaration of the author, like «я автор проекта и пишу свои образцы» ("I am the project's author and write my own samples") on the measurement draft (`docs/architecture.md` of `canvas`, `main`, read 2026-11-11). The form gives the author's samples the same proof of the license and of clause (a) of the DCO as a volunteer's.
- **By hand, without AI and without agents**: before the check a sample may carry a name. An agent is not given eval samples outside the repositories, and the form allows a run at an AI provider only for a published sample, in CI. So no session reads a person's sample in the working copy either.
- **Not editing a sample with a name**: erased strokes change the sample on which the markup stands, and take it out of clause (c).
- **The flat layout**: the protocol set the sample's ID "so that it can name the sample's file" ([contracts text](../spec/contracts/README.md)): for a person's sample it is random, and for a synthetic one it is derived from the seed, so the name says nothing about the person. The path repeats no other field of the file, and they have nothing to diverge from. The samples of a task whose open view a pull request changes are named by the runner's refusal.
- **Nothing starting with `.`**: `sample-check` will not see such a file, and the repository will publish it forever, like any other. A child sample under such a name — `eval/.drafts/x.json` — would land in git unchecked. One rule closes both `.json` and a file of any other kind. `.gitkeep` is not needed: git keeps no empty folders, and `eval/` appears with the first sample.
- **The runner's rule**: an eval set has no published form — it is outside the package — so only git sees an edit of it. An edit of the package changes the verdict by which false alarms are counted, and a new tag of `tutor` changes the prompts, the models and the runner. A branch is up to date before the merge, so the same tree that the pull request ran lands on `main`.

— *Rejected:*
- the volunteer opens the pull request themselves, from their own account: the sample is published before the check, the tie to the account stays forever, and the account says nothing about age — the arguments above;
- both ways: each would keep its own drawbacks, and there would be two checks;
- a random number of the form on the sample in git — the argument above;
- the declaration and a document that the organizer looks at — the argument above;
- an author's sample without a form, by their DCO sign-off alone: the samples page has no declaration of the author for the eval set; a request to `canvas` for one — the author's samples would wait for one more task of `canvas`;
- looking for a name on a sample with AI or an agent, and checking the sample only at the review of the pull request — the arguments above;
- a check of a sample's validity of its own in CI of `modules`, and a command of the runner of `tutor`: the rules of validity would be written a second time. The rules of the eval set `modules` does not write itself either: "MUST NOT write a check of its own" ([contracts text](../spec/contracts/README.md));

**R10. The CLI of `module-kit` stands in the stage `toolchain-core` of `.devcontainer/Dockerfile`, under `toolchain`, as the binary of a release at an exact tag, by its sha256 sum on amd64 and arm64. This is how the container of `modules` differs from the container of `spec`. CI checks the tree `modules/` and each module with the commands `check` and `build`, and the binary's signature with the recipe `release-verify` on every run. The recipes are written in bash in the root `justfile`, and their tests in `node --test`.**
- **The binary.** `ARG MODULE_KIT_VERSION`, `MODULE_KIT_SHA256_AMD64` and `MODULE_KIT_SHA256_ARM64` stand in the stage `toolchain-core`, and the CLI is installed by the same `RUN` as Node, just, Go and buf; the stage `toolchain` is built over it and holds the CLI too. The install goes by the same `fetch` as buf's: the linux binary lies in the release as it is, without an archive ([the release v0.2.3 of `module-kit`](https://github.com/altnovatrail/module-kit/releases/tag/v0.2.3)). The sum is checked before the install, as for every archive the Dockerfile downloads. Then the first line of `module-kit --version` must be `module-kit <tag>`, otherwise the build stops. The sums are taken from the release's `SHA256SUMS`, which passed `release-verify` before they were written down, as signed by the shared `release.yml` of `.github`. Dependabot sees neither the tag nor the two sums, and they are raised by hand, together. The Dockerfile is not in the release's `paths`, so raising the CLI gives no release.
- **The recipes** (`justfile`):

Each folder it gives to `module-kit check <module>`, then to `module-kit build <module> <folder>` into a temporary folder. The ID from the package's `inventory.json` ([format text](../spec/format/README.md)) must be `novatrail/<folder>`. If one module is refused, the check of the others goes on, and the recipe fails at the end. Without `modules/` the recipe prints `modules/: no modules yet` and exits with code 0;

— *Rejected:*
- the newest release by `releases/latest`: "latest" is a mark of GitHub that can be set by hand, not the greatest tag;
- the REST API for the list of releases: a token or its rate limit, and the comparison does without a token;
- downloading the archives of all the modules of the index: `diff` needs only the versions of the modules that are being checked;
- `file://` and a substitution of addresses, so that the tests go through `_published` without the network: the path `curl --proto =https` would have to be weakened for the sake of the tests;
- accepting only names without `./`: how the archive is built is the release's, and `diff` reads the same three files;
- failing on a tag without an index, as on any failure: the tag cannot be deleted, and CI would stand until a manual intervention in `.github` or the settings;
- taking the newest tag without asking for the index and failing without it — the argument above.

— *Consequence:* `justfile`; `test/published.test.mjs`; `.github/workflows/ci.yml` — the comment of the job "Modules"; CLAUDE.md; [architecture.md](architecture.md) — the checks of CI, what to build and the sources.

## The port of standalone's tasks

**R12. standalone's tasks are carried over into the module by the converter `tools/port` — Go code of this repository, the module `github.com/altnovatrail/modules` with `go.mod` at the root. It writes an answer of any kind, number or not. The key and the trap values are proven by standalone's own test bench in its temporary clone, at the commit that the batch names. What a person writes lies in the overlay files `tools/port/overlay/<batch>/<id>.yaml`, and the converter writes the task file whole and the same on every run. It draws standalone's pictures as PNG — those of the tasks, of the lessons and of the instances of templates. The code is checked by the shared `go.yml` of `.github`, and the coverage goes to Codecov.**
- **The command** — `go run ./tools/port --standalone <clone> --batch <batch file> --overlay <overlay folder> --module <module folder> [--prove] [--check] [--go <command>] [--git <command>]`: the command `go` of the test bench and the command `git` of the clone's check come by flags, by default from `PATH`, and the tests substitute them. The recipe `just port <module> [--batch <file>] [--overlay <folder>] [--check]` clones standalone at the batch's commit into a temporary folder, since MathTrail's repositories are never cloned into a NovaTrail one, takes the overlay folder by the batch's name and calls the command with `--prove`: a batch is run with one command, `just port modules/olympiad-math --batch tools/port/batches/<batch>.yaml`. The mode `--survey`, with `--commit` and `--except`, and its recipe `just port-survey` run the tasks that no batch names. Codes: 0 — written or matched, 1 — `--check` found a mismatch, or a task of the run was refused, 2 — could not.
- **Provenance.** The clone must stand at the batch's commit, without changes of its own: `git rev-parse HEAD` and an empty `git status --porcelain`, git without the caller's settings. Otherwise the converter writes nothing: the tasks, their header and the test bench are all from one commit.
- **The batch** — `tools/port/batches/<name>.yaml`: the full SHA of standalone's commit, the tasks' canvas, for each skill its techniques and anchor skills, for each task its `units`. `first.yaml` is the 27 tasks of the first batch, with the units and techniques that the first batch of [architecture.md](architecture.md) lists; every other batch is a file of its own, by its skill.
- **The task** — by the table of what becomes what in the port of standalone of [architecture.md](architecture.md):
  - the topic is `skills.primary`, the band `grades-<a>-<b>`, the difficulty the same; a topic not from `content/catalogs/topics.json`, and an unknown field of that catalog, are a refusal;
  - `question` is the first part of `statement`, the picture the second; `solution` and `solution_total` are the parts of `solution`; the task's `idea` is read and not carried over;
  - a correct option in the format's number notation — an integer or a decimal without leading zeros, with a unit from the batch's `units` after a space or without one, — is an answer slot `anywhere` with the check `number`, and a simple fraction `a/b` is one with `fraction`. The key is no longer than 16 characters;
  - the question "Which of these…" is an answer slot `choice` by tapping, with five options and the key — the text of the correct one. A correct option of another kind — a word, a time, a date, and a number with words but without the batch's `units`, — is a choice too, by hand or by tapping as its kind of answer has it, and the report names it as a non-number. Options of a choice that are equal in the normal form are a refusal;
  - a wrong option that the check reads is a trap value, with standalone's explanation or a replacement from the overlay file: for `number` this includes a simple fraction, and for `fraction` only a simple fraction. An option that the check does not read — a word, a time, a number with a foreign unit, — gives its trap into the task's `traps`, and the report names it: its explanation is not carried over. A value is no longer than 16 characters, and none equals the key or another value in the sense of the check. An explanation or a text of the overlay file that names the key of a choice, and an `answer_form` that names the key of any answer, are a refusal;
  - a task of a topic that is solved from the picture without a picture is a refusal; fields of a kind other than the converter knows are a refusal too.
- **What the overlay may say of the key.** `givens` and `unknown` retell the statement, and a word key written by hand always stands in the question, since a word is written by hand only when the question names it. So they may name a key that the question names — beside another option, or in the words of the question itself: "The beads go red, blue, red, blue" and "The first bead is red." are a retelling, not an answer. "In the words of the question itself" means in a fragment of the question with, besides the key, at least three more words, the signs of a sentence's end — `.`, `!`, `?`, `;`, `:` — dropped: so the `givens` "13 February 2026 is a Friday." match the question of `cal-56-d1-2`, "13 February 2026 is a Friday, and …", and the scrap "a Friday." names only the key. The converter refuses `givens` or `unknown` that name the key in a task whose question does not name it — "Ben runs slowest.", which is not in the question and has no other option, is an answer —, and any `simpler_case` that names it. `task.no-leaks` does not look for a key that stands in the statement ([format text](../spec/format/README.md)), so such a retelling gives nothing away. The picture does not count here, unlike in the check of the `alt` of a task solved from the picture: this is stricter than the format's check.
- **The leading question.** standalone's hint is the task's `leading_question`, word for word, at the root of the task after `unknown`: format 0.4 gives the task this closed field, which `api` gives on "Hint" before the first wrong answer, and `task.no-leaks` looks for keys in it ([format text](../spec/format/README.md)). All 311 hints are carried word for word, the 53 instructions that do not end in "?" too: they break the task down, as the format wants, and "question" is the field's name.
  - The key of a choice and of a time the converter looks for in the question itself — by the same search as in the explanations, a time also with a leading zero, — without the exceptions for a retelling of the statement that `givens` have: the question comes before the first error and gives away more than a technique does. One found is a refusal: "its leading question names its key … rewrite it in the leading_question of its overlay"; the run writes the question, names it in the report and counts it in the summary. The format does not do this: it looks nowhere for the key of a tapped choice or for a key that the statement shows, like a word from the question.
  - The key of a number and of a fraction is looked for by `task.no-leaks`, except a key that the statement shows: the format looks for it nowhere, since a question that names it shows no more than the statement. So `game-56-d2-1` ("1, 2 or 3 stones" with the key 1 and the same numbers in the statement), `game-56-d3-3`, `grid-56-d4-2`, `pct-56-d1-1` and `wp-56-d2-1` stay word for word.
  - The overlay field `leading_question` stands in the hint's place, and an overlay file with it for a task without a hint is a refusal, like `picture_alt` without a picture. A question cannot be removed by an overlay file: a leak is rewritten. Five are: in `ord-56-d3-3` and `ord-56-d4-3` the question named the key word — "Dev", "Abby", — and the converter refused, and in `game-56-d3-1`, `game-56-d4-3` and `par-56-d5-2` the key's number, which is not in the statement, stood among the numbers that the hint says to try — "1, 2, 3 or 4", — and `task.no-leaks` found it. The new texts lead the same way without the key, and no number is spelled out as a word to hide it from the check.
- **The overlay file** — `givens`, `unknown`, `simpler_case`, `leading_question`, `answer_form`, `techniques` in place of the skill's techniques, extra `traps`, `leak_phrases`, `picture_alt` and `solution_picture_alt`, `trap_texts` by trap value. Each batch has a folder of its own, `tools/port/overlay/<batch>/`: the converter refuses an overlay file of a task that the batch does not name, and in one folder a new batch's files would break another's. A refusal, so that an edit is not lost silently: there is no overlay folder, it holds a folder, it has an unknown field or a file of a task that the batch does not name, a replacement of the text of a value that the task does not have, an `alt` of a picture that does not exist. A picture without `alt` is a refusal too.
- **The task file** is written by a small YAML emitter of its own under the format's restrictions on YAML ([format text](../spec/format/README.md)): keys without quotes, strings in double quotes as JSON writes them, without `\/`, integers. The header comment names standalone's commit, the topic file and the overlay file in the batch's folder. The comment does not get into the package.
- **The converter's files** of a task are `tasks/<id>.yaml` and its two pictures. Such a file of a batch's task that the run no longer writes is stale: `--check` names it, and the run removes it. The tasks of other batches the converter does not touch.
- **The check against the solver** — `--prove`: `go -C <clone> test ./content -run '^TestEveryReferenceTaskProvesItsOwnAnswer$/^(<ID>|…)$' -count=1 -json`. The test bench runs the task's solver in standalone's sandbox, twice with the letters swapped, requires exactly one letter and checks it against `correct_answer` ([`content/solver_test.go` at 89986bc](https://github.com/mathtrail/mathtrail-standalone/blob/89986bc/content/solver_test.go)). The converter requires `pass` of the subtest of each task of the batch and otherwise writes nothing, and a refusal carries the output of the subtest that failed and the build output of `go test -json`. The key is the number of the correct option, so the test bench proves the key and that no trap value equals it. The test bench of 42b4408 proves its tasks with the same test as that of 89986bc ([at 42b4408](https://github.com/mathtrail/mathtrail-standalone/blob/42b4408/content/solver_test.go)).
- **The pictures** — `media/pictures/<id>.png`, and the solution picture `<id>-solution.png`. What is shared is in `tools/port/picture.go`: a kind of picture is read strictly, by its own `$defs` in [`content/schemas/task.json` of standalone at 42b4408](https://github.com/mathtrail/mathtrail-standalone/blob/42b4408/content/schemas/task.json), and checked against what standalone's service checks (`internal/domain/picture/`) and the schema cannot name. The names of members are checked exactly, since `encoding/json` by itself would let through `TIME` in place of `time`, and a member named twice; the keys of `marks` of a grid and of a calendar, at the top level of the picture alone, are data — names of cells, "A1", and days — and are checked only for repeats. Each kind is a file of its own, with the check, the size and the drawing. The drawing surface — with `outline`, the contour of a circle without fill, so that the Euler circles do not erase each other —, the font Go Regular of any size and the writing of PNG are shared by all the kinds. The drawing is on a white opaque background, with twice as many pixels as CSS px, with the anti-aliasing of [`golang.org/x/image/vector` v0.47.0](https://pkg.go.dev/golang.org/x/image@v0.47.0/vector). The PNG has only IHDR, IDAT and IEND, a large picture in several IDAT chunks (sources 3.3), and the bytes are the same on every run: they go into the package digest. The four kinds of the tasks solved from the picture, `lattice`, `tiles`, `shapes` and `stairs`, are decided together with the `alt` of those tasks; the other twelve:
  - `row` — standalone's description read strictly: 2–12 objects, each with the mark `dot`, `ring` or `square`, labels above and below, or a gap — not the first, not the last and not next to another ([`content/schemas/task.json` at 89986bc](https://github.com/mathtrail/mathtrail-standalone/blob/89986bc/content/schemas/task.json)); the row has `line`, `gaps`, `span` and `copies`;
  - the drawing of the rest follows the picture of standalone's card (`web/src/design/picture/`), without its layout of labels;
  - `clock` — a dial of 200 × 200 CSS px with the numbers 1–12 and minute ticks; the hour hand is shifted by the minutes, a time after 12:59 is as on a twelve-hour dial; the label of a hand is beside it, on the side where there is no other hand, and for hands that lie together, on opposite sides;
  - `table` — the header on a grey background, a column as wide as its longest cell; each row is as long as the header or the first row;
  - `bars` — at one scale, a unit no longer than 28 CSS px, and the longest bar no longer than 400. A bar's length is `length`, otherwise the sum of the segments or the number of parts. Parts or segments, not both, no more shaded than there are parts, and a bracket lies within the bar. Shaded parts are grey. Brackets are under the bar, in rows without overlaps. Notes are under all the bars;
  - `number_line` — `to` greater than `from`, the step reaching `to` in whole steps, 2–16 ticks, a mark on a tick, one per tick. Ticks with numbers under them, negative ones with a minus sign, and an arrow to the right; a mark is a dot on a tick, and its label is above it;
  - `calendar` — the names of the days in English, from Monday or Sunday; the day of a mark is written without a leading zero and is in the month; a day with a mark is in a frame, and the label is under it;
  - `containers` — no more poured than the capacity. Open at the top, standing on one floor, as high as their capacity at one scale, without ticks on the walls. Water is grey. How much is poured — in the water, and where it is shallow, above the water or above the container. The capacity is under the container, the mark above them all;
  - `grid` — the names of rows and of columns do not repeat, and those joined into a cell's name do not give two cells with one name; a shaded cell and a mark are cells of the grid, and a shaded one only once. Square cells, the names of rows on the left, of columns at the top, shaded cells grey, a mark in its cell;
  - `piles` — a gap is not the first, not the last and not next to another, and holds nothing but itself, and `shown` is only on a pile with a count, from 2 to one less than the count. Counters as circles or squares, dark or light, with a space after each group. A line breaks between groups. A cut pile is half the counters, an ellipsis and the other half; a pile without a count is a counter, an ellipsis, a counter; an empty one is a dashed place. The mark is before the pile, the value after it. Piles go one under another or, with `across`, side by side, in a shared box with `box` and in a box of their own with `boxed`; a gap is three dots. The number of counters is not written: the counters show it;
  - `venn` — two circles in a frame. Above each, its mark and how many are in it, "F: 15"; how many are in both — in the intersection; in neither — in the lower corner of the frame; the total — on the upper side of the frame;
  - `balance` — two pans on posts above the beam, weights with marks in rows of two from the pan upward;
  - `ring` — places as circles numbered from 1 at the top clockwise, and arrows on the ring between them. The start place is grey, and its mark is in the middle of the ring, with an arrow to it.
- **The pictures of lessons** — the mode `--pictures <folder> --module <module>` takes each file `<name>.json` of the folder — a picture in standalone's schema of pictures — and draws it, as it draws a task's picture, into `media/lessons/<name>.png` of the module, without a clone; extra files of `media/lessons/` it deletes, and with `--check` it writes nothing and names each file that differs. The data of the module's lesson pictures lie in `tools/port/pictures/<module folder>/`, and the recipe is `just lesson-pictures <module> [--check]`. The size of a picture in a lesson is half the size of its PNG, as for a task's picture, and the test `test/lesson-pictures.test.mjs` checks it: a lesson is written by hand, and a picture can be redrawn. The checking and the writing of files are shared by the mode and the carrying over of tasks, the functions `filesDiffer` and `placeFiles`.
- **The pictures of the instances of templates** — the mode `--template-pictures` and the recipe `just template-pictures <module> [--check]`. Each template of the module whose picture path holds placeholders takes the source `tools/port/template-pictures/<module folder>/<path without pictures/, placeholders and .png>.json`:
  - a picture in standalone's schema, like the pictures of lessons, with placeholders `{name}` in the strings, or a list of variants `[{"when": {…}, "picture": {…}}]`, where the picture changes not only by numbers: so the solution of `changes` has five shares at 20% and four at 25%, and the solution of `groups` is without the line "…" when there are three full rows;
  - or a function of the template's solver, `{"solver": "<function>"}`. The port executes the program of the solver once in the format's dialect of Starlark — the options `Set`, `While`, `TopLevelControl` and `GlobalReassign`, without `Recursion`, a budget of 100,000,000 steps per template ([format text](../spec/format/README.md)) — and on each instance calls the function with a frozen dictionary of the numbers by names in the order of their codes; `print` writes nothing. For the picture of the statement the dictionary has the numbers that `solve` gets — those whose placeholders stand in the open fields —, so the picture is exactly what `solve` reads; for the picture of the solution, which `solve` does not read, all the parameters and derived numbers. The function returns a picture in standalone's schema, which the port encodes with `go.starlark.net/lib/json` and draws as a picture from a file, by the same names of members and kinds. So are drawn the templates whose standalone solver reads the picture: `solve` builds the figure with the same function and computes on it. A refusal: the template has no solver; there is no such function; it returns not a dictionary, or one that JSON does not hold; the program does not execute — `load`, recursion, the budget; the source has other members.

  The instances the port computes itself — `module-kit` does not list them, and `build` will not pass without the pictures: the parameters by names in the order of their codes, as an odometer, the derived numbers and the constraint, by `starlark.EvalOptions` of `go.starlark.net` at the version of the format's dialect, which `go.mod` pins. The count is checked by `test/templates.test.mjs` against the package of `module-kit build`: each instance has its own file, and there are no other files of this path. A placeholder is only a parameter or a derived number; a result of the solver is a refusal, as is a source that no template names, and a variant that does not fit an instance. Extra files of the templates' paths in `media/pictures/` the mode deletes, and with `--check` names; it does not touch the pictures of tasks, as `port` does not touch the pictures of instances. The instances of a picture are painted, padded and encoded on a pool of as many goroutines as Go runs at once, one per core, and each use of a face of the labels holds its lock, as a face is not safe for concurrent use; the bytes are those of one goroutine. On one core 857 pictures are drawn and checked in ≈ 47 s.
- **Dependencies** — `golang.org/x/image`, BSD-3-Clause, as in `module-kit`, with its `golang.org/x/sys`, BSD-3-Clause; `golang.org/x/text`, BSD-3-Clause, directly, for the sake of `unicode/norm`; `go.yaml.in/yaml/v4`, Apache-2.0 with MIT files from libyaml, only for reading the batch and the overlay files; `go.starlark.net`, BSD-3-Clause, for the templates. Their versions are in `go.mod`. All are compatible with Apache-2.0, and `ci-licenses` lets them through.
- **CI.** The job "Go" calls the shared `go.yml` of `.github` at the release that `ci.yml` pins, without the input `same-bits`. Its jobs take the image of the `toolchain` stage and the caches of Go from the cache of GitHub Actions, which a push to `main` saves, and on a miss of the image its job "Go / toolchain" builds the stage once for the others ([`go.yml` of `.github` v0.1.30](https://github.com/altnovatrail/.github/blob/v0.1.30/.github/workflows/go.yml)). The checks — "Go / lint", "Go / test", "Go / vuln" and "Go / licenses" — run by the recipes `ci-lint`, `ci-test`, `ci-vuln` and `ci-licenses` of the `justfile` ([`go.yml` of `.github` v0.1.15](https://github.com/altnovatrail/.github/blob/v0.1.15/.github/workflows/go.yml)), after the pattern of `spec`: govulncheck and go-licenses through `go run`, at the versions the `justfile` pins. `ci-test` keeps `-race`, and the tests of the pictures of every kind run as parallel subtests, so that it sees them drawn at once. The profile `coverage/go.out` goes to Codecov by OIDC. `.github/codecov.yml` is the text of `.github`'s template: `codecov/patch` ≥ 90%. Go is not in the release's `paths`. The README carries no badge of the language: the code is a tool of the port, like the check tools of `spec`, not code of the platform.
- **Tests.** The Go tests are `tools/port/*_test.go`, on tasks in standalone's form with texts of their own: they do not read `spec/`, which `go.yml` does not take. They are the cases of the table — an integer, a number with a unit, a fraction, "Which of these…", a non-numeric wrong option, — the refusals, the overlay file, the pictures, the test bench with a substituted `go` and the command itself; the coverage is 97%. The Node test `test/port.test.mjs` in the job "Modules" writes tasks with a picture into a module from the format examples `olympiad-math`, and `module-kit check` accepts it without warnings.

— *Why:*
- **Go in the repository**: Go already stands in the `toolchain` stage, the picture is drawn by its standard library with `x/image`, and the whole port carries its tasks with the same code. The shared `go.yml` gives the checks and the coverage without a CI of its own.
- **standalone's test bench**: the solvers call the helpers of its sandbox — `match`, `product`, `combinations`, `days_in_month` and more. A go.starlark.net of our own would have to be extended with these helpers, and it could diverge from what standalone has already proven. standalone is frozen, and its test bench at the commit a batch names does not change.
- **Overlay files**: a converter corrected after the batch writes its tasks anew, and what was written by hand is not lost; `--check` catches a task file edited by hand.
- **An emitter of its own**: under the format's restrictions a small subset of YAML is written, and its bytes do not depend on the version of someone else's library.
- **`containers` without ticks**: standalone's service puts a line on the wall of a container for each unit, but every task of standalone with this picture is a pouring task, and six of them say outright "The jugs have no marks": with ticks a child would measure 2 litres in one step, and the picture would argue with the statement. The capacity and the amount are still written as numbers.

— *Rejected:*
- Node in `tools/port/`: a PNG with labels needs npm packages, a lock file and the check of its licenses;
- code outside the repository: the rest of the port would write it anew, and it would have no tests in CI;
- running the solvers on a go.starlark.net of our own with the format's dialect, in place of the test bench — the argument above;
- "the first run, then by hand": a fix of the converter would not reach the tasks already written;
- only the standard library for PNG: a font of digits of our own would have to be drawn and maintained;
- letting the key into any `givens` of a task whose question names it: `givens` that simply say the answer pass that way;
- for "the words of the question itself", dropping only the full stop — "Friday." passes that way; comparing with whole parts of the question between punctuation marks — "and its 1st day is a Monday" would not match "Its 1st day is a Monday.";
- for the leading question: rewriting the 53 instructions as questions — 53 edits of standalone's text; not taking them; looking for the key of a choice in it only by proofreading — the leak would be found by a person or by no one; letting the key into it beside another option or in the words of the statement, as in `givens` — the question does not retell the statement but leads to the answer;
- drawing the ticks of `containers`, as standalone does — the picture contradicts the task; drawing them by a flag of the batch — there is not one task with ticks;
- drawing the lessons' pictures with a script outside the repository — the PNG in the module could not be checked against the data; drawing them with the code of standalone's site, with Preact components, — that is the build of the site, and the data of the site's drawings are the same `lattice` that the converter already draws;
- for the instances: a parsing of expressions of our own in place of `go.starlark.net` — a second dialect, which could diverge from the format; their numbers from the package of `module-kit` — the package cannot be built without the pictures; a source per instance — 483 data files instead of six; variants `when` for each instance in place of a function of the solver — 26 pictures of lattices and sticks by hand, which nothing checks against the solver.

**R20. The converter writes an answer that is not a number by its kind. A time on a clock `H:MM` is the check `time`. - **The kind of the answer** — the order of `answerOf`, by the correct option, by the format's kinds of check:
  - the question "Which of these…" — a tapped choice;
  - a number or a fraction in the format's notation — `number` or `fraction`. ## The guard of the eval set

**R25. CI checks the `eval/` of each module with the recipe `just eval-check`, a step of the job "Modules", on every pull request and push to `main`, and from a fork too. The recipe holds the layout `eval/<id>.json` — the name of a file is the field `id` of its sample, and `eval/` holds no folder, no link, no other file and nothing named with a dot, at any depth, — and calls `just -f spec/justfile sample-check --eval-set novatrail/<folder>` once on the eval set of each module. The next step, "eval-match", the recipe `just eval-match`, holds each sample to the package that `module-kit build` builds at this commit: a synthetic sample it draws anew with the generator of `canvas` and compares with the file, a person's sample it holds by the digest of its task's open view. A sample that does not match is refusal 1 with the file and the task: a synthetic sample is to be redrawn (`just synthetic`), a person's sample removed.**
- **What `eval-check` holds:**
  - only the folders `modules/*/` are read: a file, a link and a name starting with `.` in `modules/` are rejected by `modules-check`, and the recipe does not name them a second time, while a `modules` that is not a folder the recipe rejects itself. A module without `eval/` passes;
  - an `eval` that is a link or not a folder is a violation, and so is anything under `eval/` whose name starts with `.`, at any depth. In `eval/` — without descending — a folder, a link or a special file is a violation; a name other than `<id>.json`, where `<id>` is 1–64 lowercase Latin letters, digits and hyphens, is a violation; a file that holds not exactly one JSON value — an object with a string `id`, — or whose `id` is not its name, is a violation. The ID is matched against the name by `jq` itself, not by the shell, which would cut off a newline and a NUL at the end of `id`, and the class `[a-z]` the recipe reads in the locale `C`, where it holds no letters with diacritics;
  - **the eval set** goes into the mode as the protocol names it: each regular file `*.json` under `eval/`, at any depth, but those under a name starting with `.`. Links do not go: the layout rejects them, and a link outward would stop `sample-check` with status 2. A module without such files does not call the mode: `sample-check` stops a call without a file with status 2. The mode is called even on a violation of the layout, so that one run shows everything;
  - **one call a module**, on all the files of its eval set, in order: the check holds whole only the file it reads, and one call checks hundreds of large samples (measurements 3). That no two samples share an ID the tool holds itself, and the flat layout holds it too: the ID is the file's name in one folder;
  - the refusal of one module does not stop the check of the others. The code is the greatest of what failed: 1 — a violation of the layout or a refusal of the mode, 2 — `jq`, the tools of `spec` or the mode could not do their part, and without `jq` the recipe goes on through the other modules. The tools of `spec` are installed by a separate call `just -f spec/justfile _tools` before the first set: `npm ci` fails with status 1, like a refusal of the mode, and otherwise they could not be told apart. After it a status above 2 is also 2. A folder whose name gives no module ID stops the mode with status 2, and `modules-check` rejects it in the same job;
  - the network only for the tools of `spec/tools`, which it installs from the lock file through npm, as `docs-check-repo` does; no key and no writing into the tree, so a pull request from a fork passes it. The step of CI runs even when the step before it failed — but the build of the `toolchain` stage, — so a refusal is seen from the first run.
- **What `eval-match` holds:**
  - **a synthetic sample** is drawn anew with the generator of the stage — with the tag from the file, not with the newest, — and compared with the file in everything but `task.modules.version` and `task.modules.package_digest`. The protocol says: "The tag, the version and the package's digest that the sample names say only what it was made on, and are not compared, but the digest of the task's open view MUST be the sample's". The tag is compared, but matches by itself: the drawing is made with the file's tag;
  - **a person's sample**: its `task.open_view_digest` against the digest of the task's open view — for a template, of the instance by `task.seed` — by `module-kit open` over the commit's package. `open` opens an instance by the seed and gives the digest of each task by the same projection by which the runner reads the task, and the generator of `canvas` was checked against it. The index for `open` is `module-kit index --first` over the commit's package, and the command requires the seed `--seed`, so without seeds `--seed 0` goes: it does not touch the instances of templates. Checked 2026-11-10: the digest of `times-tables-d3` is the same at `open` and at the generator of `canvas`;
  - **the generator is called in groups** — by tag and no more than 50 calls a group: it holds all the samples of a call in memory. A group that the generator rejected the recipe draws anew one sample at a time, and each file gets its own reason from the generator, word for word, with code 1 — for example, the task became a template or disappeared;
  - **what the recipe reads** — only fields, with `jq`: the origin (`synthetic` or `person`), the module, the task, the seed, the tag and the digest; it does not print a person's sample. A file outside the layout `eval/<id>.json`, a file without these fields, a sample of another module and a synthetic sample without a seed or a tag are refusal 1, though `eval-check` rejects them too: so not one sample passes without the check. Seeds up to 2^64 the recipe compares as strings, not as numbers. A module without samples is not built. The code is the greatest over the modules, and it is never above 2: 1 — a mismatch, 2 — `module-kit`, the generator or `jq` could not. There is neither network nor key: a pull request from a fork passes the step;
  - in a temporary copy with 631 synthetic samples of `olympiad-math` (322 MB), 2026-11-10, `eval-match` took 42 s; the job "Modules" has a limit of 20 minutes.
- **The tests** run the real `sample-check` — the `spec/` of a made-up repository is a link to the submodule of this one, — and a substitute `spec/justfile` is needed only for the form of the call and the statuses. A call costs 0.4 s (measured 2026-11-09).

— *Why:*
- **By code**: a sample that got into a branch is already published, and only GitHub Support can remove what remains of it ([GitHub Docs, Removing sensitive data from a repository](https://github.com/github/docs/blob/e0b0c90/content/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository.md)). By hands alone, the file of a child's measurement — `WRITER_CHILD` with the writer code — would pass CI into the `eval/` of a module.
- **Nothing named with a dot**: the protocol does not count such a file as part of the eval set, but the repository publishes it the same way, forever, and a child's sample under such a name would land unchecked.
- **One recipe for the layout and the set**: one step of CI, and one place where the files of the set are listed.
- **JSON by `jq`**: it is in the `toolchain` stage, and the recipes `_entries`, `_modules-check` and `release-files` already read the index and the inventory with it. It takes only `id` and the fields that `eval-match` needs: the strict reading of a sample, the rules of the sample file and of the eval set are `sample-check`'s, and `modules` writes no check of validity of its own.
- **Each sample to the commit's package**: a pull request that changes a task's open view remakes its synthetic samples in the same pull request and removes the people's samples, as the protocol requires, and only a check on the commit sees it.

— *Rejected:*
- the layout only, without the mode — the rules of the sample file would be held by hands;
- a check in `modules-check` — it has its own meaning, `module-kit` and the package, and `eval/` does not go into the package;
- a separate recipe and step for the mode — two places where the files of the set are listed;
- `node` for JSON — a second way to read JSON in the recipes; a parsing of the protocol of its own — the very check of validity that `spec`'s tools hold for every repository;
- a substitute of `sample-check` everywhere in the tests — the test would not see what the mode accepts and rejects in fact;
- chunks of 50 files a call of the mode — one call holds hundreds of large samples (measurements 3), and `xargs -n 50` would replace the codes 1 and 2 with its own 123;
- a byte-for-byte comparison of a synthetic sample — against the protocol, and hundreds of samples would be redrawn without an edit of their tasks; a check of synthetic samples only by the digest — the drawing is changed both by the task's picture and by a new version of the generator, while the open view may stay the same;
- the digest of a person's sample from the generator's `--digest` — it gives a template no digest ("no open view, being a template"), and the author's samples are above all on templates; a projection of its own — a third implementation of the open view.

— *Consequence:* `justfile` — `eval-check`, `eval-match`, `_match-synthetic`, `_match-people`, `_pinned-module-kit`, `_generator`; `.github/workflows/ci.yml`; `test/eval-check.test.mjs`, `test/eval-match.test.mjs`, `test/synthetic.test.mjs`, `test/helpers.mjs`; `.claude/rules/eval.md`; CLAUDE.md; [architecture.md](architecture.md) — the checks of CI and the samples in the eval set.

## The generator of synthetic samples

**R29. The synthetic samples of a module's eval set are written by the recipe `just synthetic <module> <task>:<seed>...` with the generator of `canvas` — the file `synthetic-module_<tag>.mjs` of a release of `canvas` at an exact tag. The file stands in the stage `toolchain` of `.devcontainer/Dockerfile` by its tag and sha256 sum, like the CLI of `module-kit`, and is run by the Node of the stage `toolchain-core`. CI checks the release's signature with the recipe `canvas-verify` on every run, and its step "eval-match" draws each synthetic sample of an eval set anew with the same file. The recipe builds the module package with `module-kit build` into a temporary folder and calls the generator with the tag of the newest release of `modules`; the generator writes the samples into the module's `eval/`. This is the second difference of the container of `modules` from the container of `spec`.**
- **The generator** — every release of `canvas` since v0.3.6 carries `synthetic-module_v<X.Y.Z>.mjs` — one ES module for Node 24 without npm packages beside it, with the signature of the shared `release.yml` and in `SHA256SUMS` ([altnovatrail/canvas, release v0.3.6](https://github.com/altnovatrail/canvas/releases/tag/v0.3.6), read 2026-11-10). It has two forms of the call:
  - `node <file> --module <package> <tag> <folder> <task>:<seed>...` writes synthetic samples into the folder. All the calls it checks before writing: if one has not passed, it writes nothing. A person's sample it never overwrites. The exit codes: 0 — written, 1 — a refusal with a reason for each call, 2 — a call not of the form;
  - `node <file> --digest <package> <task>...` prints the task's ID and the digest of its open view — by the same projection by which a sample names it.

  The file asks for no network: it has only `node:fs`, `node:path` and `node:crypto`.
- **How it gets into `modules`.** In the stage `toolchain`, by a `RUN` of its own over `toolchain-core`, where `module-kit` is, stand `ARG CANVAS_VERSION` and `ARG CANVAS_SYNTHETIC_SHA256` — one sum for both architectures, because there is one file. The same `fetch` that downloads the rest checks the sum before the install and puts the file into `/usr/local/lib/canvas/synthetic-module_<tag>.mjs`. The sum is taken from the `SHA256SUMS` of the release, which `just -f spec/justfile release-verify canvas <tag>` accepted before the sum was written down. The Node of the core is the one the generator requires. Dependabot does not see the file: the tag and the sum are raised by hand, together, and the container is rebuilt after that. No recipe of the release runs the generator, so the release, which builds the core alone, does without it.
- **The recipes** (`justfile`):
  - `synthetic` passes the call to `_synthetic` with an empty tag, and that one takes the tag of the newest release of `modules` from `_newest-release` — after all the checks that need no network: a typo in the module's name or a container that is not rebuilt is named by its own reason and does not go to the network. If there is no release, this is a refusal with status 2;
  - `_newest-release` takes the tags `vX.Y.Z` from `git ls-remote`, and the newest is the first that has a `module-index.json`; a tag whose release did not come out is skipped. `_published` calls it. The index's signature is not needed for synthetic samples: the recipe takes only the tag from it, and the index file enters neither code nor CI;
  - `_synthetic <module> <tag> <calls>...` checks in order: `modules/<module>` is a folder, and the name is not empty; `eval/` there is a folder or does not exist, but is not a link and not a file, otherwise the generator would write the samples past the module; `_pinned-module-kit` — `module-kit --version` is the one pinned in the Dockerfile; `_generator` — the sum of the generator's file is `CANVAS_SYNTHETIC_SHA256`. Otherwise a refusal with status 2 and the words "rebuild the container": a container not rebuilt after the tag was raised would write not what CI would make. `eval-match` calls the same two, so the synthetic samples are written and checked by one and the same file of the generator. Then `module-kit build` into a temporary folder, the package ID is `novatrail/<module>`, and the generator `--module <package> <tag> modules/<module>/eval <calls>`. Its lines, the reasons of its refusals and its exit code are the recipe's: a task that the generator rejects is named by its reason. The generator's folder is set by `CANVAS_LIB` — for the stub in the tests;
  - `canvas-verify` downloads the release's `SHA256SUMS` and its bundle by the public address, without a token, checks the signature through `release-verify canvas <tag>`, and `_canvas-sum` checks the generator's line against `CANVAS_SYNTHETIC_SHA256`.
- **CI** (`ci.yml`) — the job "canvas signature", `just canvas-verify`, on every pull request and push to `main`: it reads the Dockerfile and the release, not the file, and takes the image of the core. The job "Modules" waits for it together with "module-kit signature". CI calls not `synthetic` but the generator, in the step "eval-match".
- **The tests.**

It also checks that the generator's status and reasons pass through unchanged and that the recipe refuses in each of the cases: an old sum, no file, another `module-kit`, a refusal of `module-kit`, another ID, a call not of the form. All of this is on a stub of the generator whose sum the Dockerfile of a made-up repository writes.
  - One test runs the real generator of the stage and the real `module-kit` on a copy of `grade-3-math`: the sample passes `eval-check`, and a second call with the same seed gives the same file byte for byte.
  - `test/published.test.mjs` holds `_newest-release` on stubs of `git` and `curl`: a tag whose index answers 404 is skipped, another failure is status 2, not "there is no release".
  - `test/canvas-verify.test.mjs` holds `_canvas-sum` on a made-up `SHA256SUMS` and Dockerfile, without the network, as `test/module-kit-verify.test.mjs` holds the sums of `module-kit`.
